# Advent of Code 2023 — findings log

Dogfooding log for solving Advent of Code 2023 in Zhex (archive epic #136): one section per day, recording the approach, the sample answers, the runtime on the sample input, and the interpreter gaps the day hit — each gap becomes a ticket number. The truth surfaces (`aocSpecs` in `tools/site-data`, ROADMAP) are updated by the stories; this log captures the reasoning in between.

**V1 verification sweep** (#144): 23 of 25 days PASS on a clean tree — every runner exits 0 with the answers recorded below, three-way agreement holds (test literal == `aocSpecs` row == build-time Go oracle == browser wasm run), and days 10 and 14 were flagged for latent input-shape defects no committed sample reaches. Both flags were fixed and regression-pinned on main: day 10's north-connect branch (#169, 1967f6d) and day 14's exact-division jump guard (#170, efd8a13), with the full suite green after each.

## Day 1 — Trebuchet?!

**Approach.** `parse` keeps the nonempty lines; `_line-value` scans each line once, left to right, remembering the first and last digit it sees — `_digit` reads a one-character slice through `text.to-int` with a `-1` catch, and part 2 additionally consults `_word-digit`, which matches the spelled-out names against the slice from the current position to the line's end with `text.starts-with`. Scanning every position (instead of replacing words left to right) is what makes overlaps like `eightwo` count as 8 then 2: the scan sees `eight` at one index and `two` at the next.

**Sample answers.** Part 1 `142` on the public worked example (`samples/day01.txt`; matches the page). Part 2 `281` on the page's second, spelled-out example (embedded in the test); the part-1 example contains no spelled digits, so the runner prints `142` for both parts on the sample file, and the manifest records that pair.

**Part 2 sources.** The mechanics are login-gated, so two community references agreed before relying on anything: Sarah Glasmacher's walkthrough (sarahglasmacher.com, "How to solve Advent of Code 2023 – Day 1 with Python" — overlapping words count, e.g. `oneight` reads as 1 then 8, and she replaces only a word's first letter so the trailing letters stay detectable) and sanraith/aoc2023 `Day01.scala` (a lookahead regex `(?=(\d|one|...|nine))` that finds overlapping matches at every position). Both agree on scan-every-position; the part-2 sample value came from a Go implementation of that rule, which also reproduced part 1's published 142.

**Runtime feel.** ~50 ms on the sample; instant on every line.

**Gaps.** None new — the no-char-type friction (one-character slices plus `text.to-int`, and `starts-with` against the end slice instead of a starts-at offset) is the epic's known trap. The runner follows the 2025 idiom: sentinel `catch` end-of-file (#135) and the `dayNN`/`dayNN-core` split (#134); `zhex compile --target=browser` succeeds, so no WasmNote.

## Day 2 — Cube Conundrum

**Approach.** `_parse-game` splits each line at its colon, the reveals on `;`, each reveal on `,`, and each count-color pair on the space, trimming as it goes (`text.split` keeps the separator's whitespace). What stays per game is one `Game` record: the ID from the `Game N` prefix and the largest count seen per color — both parts are then pure folds. Part 1 sums the IDs of games whose maxima fit the bag (12/13/14); part 2 sums each game's maxima multiplied together, the fewest cubes the bag must have held.

**Sample answers.** Part 1 `8`, part 2 `2286` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Sarah Glasmacher's walkthrough (sarahglasmacher.com, day 2 — track the maximum observed count per color, multiply the three per game, sum the products) and sanraith/aoc2023 `Day02.scala` (`part2` folds each game's hands into per-color maxima and takes the product). The part-2 sample value came from a Go implementation of the agreed rule; the same run reproduced part 1's published 8.

**Runtime feel.** ~50 ms on the sample; nothing to measure.

**Gaps.** None new. The first `list.append(games, _parse-game(line))` draft tripped the intended checker rule — a word whose `try` can escape hands back a Result, so the call site carries the postfix `try` and `parse` stays fallible like the 2025 idiom. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 3 — Gear Ratios

**Approach.** The grid stays a list of row strings. `parse` collects every maximal digit run as one `Part` record (`_parse-row` walks a row with an index loop, accumulating the value digit by digit since there is no char type); part 1 then checks each part's bordering window (three rows by its columns plus one on each side) for a symbol — any character that is neither a digit nor a period (`_symbol-at` bounds-checks). Part 2 scans every `*` cell, collects the parts whose row is within one and whose column span overlaps the cell's three-wide window (`_touches`), and adds the product when exactly two neighbors touch. Straight neighbor scans, no recursion, so the 256-deep call limit never comes near.

**Sample answers.** Part 1 `4361`, part 2 `467835` (`samples/day03.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Sarah Glasmacher's walkthrough (sarahglasmacher.com, day 3 — an asterisk adjacent to exactly two full numbers is a gear; the ratio is their product; sum the ratios) and sanraith/aoc2023 `Day03.scala` (`part2` filters symbols equal to `"*"` with `numbers.length == 2` and sums `numbers.product`). The part-2 sample value came from a Go implementation of the agreed rule; the same run reproduced part 1's published 4361.

**Runtime feel.** ~55 ms on the sample (10x10 grid). The part-2 scan is asterisks times parts — tiny here; the real input's 140x140 stays comfortable in an interpreter.

**Gaps.** None new. Known-trap friction only: characters read as one-character slices, digits parsed one at a time. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 4 — Scratchcards

**Approach.** `parse` reduces each card to its match count: split the line at the colon, the rest on the bar, each side's numbers on spaces (`_numbers` skips the empty tokens multi-space splits leave), then count the card's numbers that appear among the winners — no `list.contains` word exists, so the check is `list.any(winning, _is(_, number))` with a two-line equality partial. Part 1 scores `2^(matches-1)` by repeated doubling (`_double`); part 2 cascades with a per-card count list seeded at one: card `index` with `m` matches adds its count to each of the next `m` cards (indexed writes inside `for ... in range` loops, never inside a list traversal), and the answer sums the counts — the iterative List-as-queue the ticket sketched, no recursion anywhere.

**Sample answers.** Part 1 `13`, part 2 `30` (`samples/day04.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Sarah Glasmacher's walkthrough (sarahglasmacher.com, day 4 — matches spawn copies of the following cards, copies spawn identically, count cards per ID in a dictionary and sum, like 2021's lanternfish) and sanraith/aoc2023 `Day04.scala` (`scratchAndCount` memoizes `1 + the counts of the won cards`). The part-2 sample value came from a Go implementation of the forward cascade; the same run reproduced part 1's published 13.

**Runtime feel.** ~50 ms on the sample. The cascade is one pass with indexed adds — the real input's 200-plus cards stay linear and comfortable.

**Gaps.** None new worth a ticket. Friction, noted: the checker's Result discipline caught two honest drafts (a fallible word's value passed to `list.append`, and a fallible call inside a `for ... in` collection position, which wants the Result handled in a `let` first); and lists have no `contains` word, so membership goes through `list.any` with an equality partial — a one-word convenience the standard-library plan does not propose, so no gap ticket; if later 2023 batches lean on it again, it becomes one.

## Day 5 — If You Give A Seed A Fertilizer

**Approach.** The known trap of the batch, planned as an interval walk before coding: brute-forcing part 2's billions of seeds is a non-starter in an interpreter. `parse` flushes map blocks into `levels` (a list of `RangeMap` records per block, blank lines skipped, headers detected by `ends-with "map:"`); part 1 walks each seed numerically (`_map-one`, `_location`). Part 2 pairs the seed line into inclusive `Span`s (first/last) and `_map-spans` carries whole spans through one level at a time: each span is cut against the first range it meets — the outside pieces return to a pending list the index loop keeps re-examining, the overlapping middle shifts by that one range's offset, and a span no range touches passes through unchanged. The final answer is the lowest span start after the last level. Span count stays tiny (each level adds at most one piece per range boundary), so the walk is symbolic and fast on any input size.

**Sample answers.** Part 1 `35`, part 2 `46` (`samples/day05.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Nicky Meuleman's walkthrough (nickymeuleman.net, "Advent of Code 2023 Day 5" — seeds `79 14 55 13` are the two ranges 79–92 and 55–67, solved by splitting ranges at map boundaries instead of per-seed checks) and sanraith/aoc2023 `Day05.scala` (`part2` groups seeds into ranges and `combineRangeMaps` walks levels by intersecting interval endpoints; the sample's part-2 trace ends at location 46 from seed 55). The part-2 sample value came from a Go implementation of the interval walk; the same run reproduced part 1's published 35.

**Runtime feel.** ~55 ms on the sample; the walk is span-count-bound, not seed-count-bound, so a real almanac lands in the same ballpark — the brute-force alternative would be billions of walks.

**Gaps.** No new ticket: the almanac's blank-line separators put this day in exactly the 2025 day-5 position — the browser build's `read-line` traps on an empty line before any `catch` could run (#155), and the canonical `error.detail` end-of-file branch is itself wasm-fenced (#135) — so the runner follows the 2025 day-5 shape and the door carries the fence note naming `error.detail` (the `-wasm` pass records it as the WasmNote). One syntax note for the log: a dot reads fields only after a bound name, so `current[0].first` wants the element bound in a `let` first.

## Day 6 — Wait For It

**Approach.** `parse` reads the two lines by prefix, keeping the per-race numbers and, for part 2, the digits of each line joined into one huge number (`text.join` over the number tokens). Both parts are the same word: `_wins` counts hold times `t` in `range(1, time)` whose `t * (time - t)` beats the record — the parabola rises then falls, so the winning holds are one contiguous run, and the count over the sample's 71530-millisecond race is immediate. Part 1 multiplies the per-race counts; part 2 runs the same count on the joined race.

**Sample answers.** Part 1 `288`, part 2 `71503` (`samples/day06.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Nils Osswald's walkthrough (nilsosswald.de, day 6 — the only change is parsing, concatenating each line's digits into one number and reusing the part-1 counter) and sanraith/aoc2023 `Day06.scala` (`part2` runs the same count over `times.mkString.toLong`, `distances.mkString.toLong`). The part-2 sample value came from a Go implementation of the joined race; the same run reproduced part 1's published 288.

**Runtime feel.** ~75 ms on the sample (71530 hold times tested). A real input's ~47 million hold times would take minutes at this pace; counting between the quadratic's roots would need an integer square root the language does not ship, and the plan defers math built-ins, so the honest loop stays — the door feeds the sample, not the real input.

**Gaps.** None new. One language note for the log: `record` is a keyword, so a parameter of that name needs renaming (`best` here). Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 7 — Camel Cards

**Approach.** Each hand collapses into one Int score so `list.sort-by` can rank it: the type tier shifted up five base-14 digits, then one digit per card. The tier comes from counting how many labels occur 0 to 5 times (`_count` scans five one-character slices, `_tier` buckets the thirteen labels) — five of a kind 6 down to high card 0, with full house and two pair the only bucket-shape distinctions. Part 2's joker is exactly sanraith's try-each: `_joker-tier` replaces every `J` with each non-joker label in turn and keeps the best `_tier`, while `_card-value` orders `J` below `2` in `AKQT98765432J`. `_winnings` walks the sorted list with its ranks.

**Sample answers.** Part 1 `6440`, part 2 `5905` (`samples/day07.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Nils Osswald's walkthrough (nilsosswald.de, day 7 — jokers join the largest group for the type and compare as the lowest card, below 2; sample 5905) and sanraith/aoc2023 `Day07.scala` (`part2` re-sorts with `CardValuesWithJoker = "AKQT98765432J"` and `handType` maxed over every card the jokers could stand in for). A Go implementation of those rules reproduced both sample values.

**Runtime feel.** ~55 ms on the sample. The joker tier tries twelve replacements per hand — five hands here, a thousand on a real input, all trivial.

**Gaps.** None new. Known-trap friction only: card labels as one-character slices and label-membership as `text.contains` over a shape string. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 8 — Haunted Wasteland

**Approach.** All node names are three letters, so `parse` slices `NAME = (LEFT, RIGHT)` at fixed columns into a `Map<String, Junction>`; the first nonempty line is the directions. Part 1 is the literal walk from `AAA` until `ZZZ`, the instruction index wrapping at the line's end. Part 2 walks each `A`-suffixed start to its first `Z`-suffixed node — that first-hit length is the walker's cycle — and folds the cycles with `_lcm` over `_gcd` (Euclid by remainder, seven lines, following `examples/gcd.zhex`).

**Sample answers.** Part 1 `2`, part 2 `2` (`samples/day08.txt`, the page's first worked example). The test also pins the second part-1 example (`LLR`, 6 and 6) and the dedicated ghost example (two `A` starts with cycle lengths 2 and 3, part 2 = 6).

**Part 2 sources.** Two agreed: Nils Osswald's walkthrough (nilsosswald.de, day 8 — start at every `A` node simultaneously, end when all sit on `Z` nodes, take the LCM of the per-path cycle lengths) and sanraith/aoc2023 `Day08.scala` (`part2` records each junction's first `Z` hit as its cycle and folds `leastCommonMultiple` over `greatestCommonDivisor`). A Go implementation of the LCM rule reproduced all three example answers.

**Runtime feel.** ~55 ms on every example. Real inputs walk a few dozen steps per start — nothing to measure.

**Gaps.** The expected engine ones, no new ticket: the input's blank separator line forces the day-5 runner shape — the browser `read-line` traps on an empty line before any `catch` could run (#155), and the canonical `error.detail` end-of-file branch is wasm-fenced (#135) — so the door carries the fence note naming `error.detail`. There is no `gcd`/`lcm` built-in; the hand-rolled Euclid matches the standard-library plan's stance that integer helpers stay concrete source words (S3 ships `min`/`max` the same way), so no gap ticket — seven lines, used once.

## Day 9 — Mirage Maintenance

**Approach.** `parse` keeps each line as a `List<Int>`; `_differences` builds the next rung down. Part 1 folds down the ladder adding each level's last number (the sum telescopes, so top-down accumulation works); part 2 collects each level's first number and folds them bottom-up as `first minus the value below` — the subtraction does not telescope, and the first draft that accumulated top-down earned the wrong sign on the sample before the fold was reversed. `list.any(level, _nonzero(_))` is the all-zero stop.

**Sample answers.** Part 1 `114`, part 2 `2` (`samples/day09.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: Nils Osswald's walkthrough (nilsosswald.de, day 9 — reverse each history and run the same next-value algorithm; the page's three histories extrapolate backwards to −3, 0, and 5) and sanraith/aoc2023 `Day09.scala` (`part2` folds the heads stack with `x - acc`). A Go implementation reproduced both sample values (2 = −3 + 0 + 5).

**Runtime feel.** ~50 ms on the sample; every history shortens by one per rung, so the ladder is quadratic in a short line and instant.

**Gaps.** None new. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 10 — Pipe Maze

**Approach.** Directions are ints 0–3 (N, E, S, W) with `_dx`/`_dy` steps. `_start` finds S by `text.index-of`; S's two connections come from `_connects-back` (a neighbor answers north/south steps with a `|LJ` shape, east/west with `-7J`/`-LF`), which also names S's true shape for the ray cast. `_marks` walks the loop from S — `_step-dir` picks the opening the entry did not use — flagging loop tiles on a flat `width * height` marker list of indexed writes; part 1 is the marked count over two. Part 2 ray-casts each unmarked tile leftward along its row (S drawn as its real shape): a loop tile crosses when it is `|`, `L`, or `J`, which nets F..7 and L..J to zero crossings while F..J and L..7 each cross once — odd crossings mean inside.

**Sample answers.** Part 1 `4`, part 2 `1` (`samples/day10.txt`, the page's first worked example; part 1's value matches the page — the square loop encloses only its center tile). The test also pins the complex part-1 example (8, one inside tile) and the two part-2 examples: the nested boxes (loop of 44, 4 inside) and the sprawling junk-pipe grid (80, 10 inside).

**Part 2 sources.** Two agreed: Nils Osswald's walkthrough (nilsosswald.de, day 10 — ray casting against the loop as a polygon, odd crossings inside; the boxed example counts 4 enclosed tiles) and sanraith/aoc2023 `Day10.scala` (`part2` scans same-row loop tiles left of each tile, counting `|`, pairing `F`-`7` and `L`-`J` corners to net zero, `L`/`F` +1, `7`/`J` held for the pair). A Go implementation of the same rule reproduced every example value, including the 4 and 10 the community quotes for the two part-2 grids. One caution for whoever revisits: the nested part-2 example circulates corrupted (an 11-wide variant with a hole in row five that yields an impossible odd loop); the test embeds the self-consistent 10-wide grid whose every pipe connects.

**Runtime feel.** ~50 ms per example. The ray cast is row-wide scans — quadratic in a row's length but bounded by the sample's 20 columns; a real 140-column grid stays under a few million inner steps.

**Gaps.** None new. Known-trap friction only: tile shapes as one-character slices and shape-membership as `text.contains` over a shape string, plus hand-rolled `_width`/`_tile` bounds care the no-char-type grid makes explicit. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 12 — Hot Springs

**Approach.** The count is a flat dynamic program, not the recursion the references use: `_count` builds one `List<Int>` table of `(prefix length + 1) * (groups + 1)` cells laid out with a manual stride, seeds cell zero at 1, and walks positions left to right — a `.` or `?` steps one cell as a dot, and a `#` or `?` may jump past the next group's run of non-dot characters plus its one separator (`fits` scans the run, `after` checks the separator or the row's end). The answer reads the last cell. Word-call depth is one for any input, dodging the recursion-plus-memoization depth bill entirely (the unfolded rows run ~120 characters, within the 256 limit but uncomfortably close to it stacked on a caller chain). `_unfold` joins five copies with `?` and repeats the group list fivefold.

**Sample answers.** Part 1 `21`, part 2 `525152` (`samples/day12.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day12.scala` (part 2 maps each line to `(records ? records ? ... fivefold, groups fivefold)` and runs the same arrangement counter) and p88h/aoc2023 `day12.py` (`run(5)` unfolds `((a + "?") * 5)[:-1]` with `c * mult` rules through the same memoized counter). The Go oracle reproduced 21 and 525152 on the sample with the prefix/table DP above.

**Runtime feel.** ~65 ms on the sample. A real input's thousand rows at ~120x36 cells each with per-cell group scans lands in the tens of millions of interpreted steps — a minute-class run in the interpreter, and the same program answers in well under a second once browser-compiled.

**Gaps.** None new. The `text.to-int` inside `parse` keeps it fallible, so the runner carries the postfix `try` like days 2 and 6. Runner shape otherwise unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 13 — Point of Incidence

**Approach.** One scan answers both parts: `_mirror` walks every fold position and counts mismatched cells across it, exiting a fold early once the count passes the wanted number; part 1 wants a perfect fold, part 2 the fold holding exactly one mismatched cell pair — precisely one smudge flipped, without ever enumerating flips. Vertical mirrors are the same word over `_transpose`d rows, so the summary is `100 * _mirror(rows, want) + _mirror(turned, want)` per pattern. `parse` reuses the 2025 block-splitting shape (a `var` row list flushed at each blank line).

**Sample answers.** Part 1 `405`, part 2 `400` (`samples/day13.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day13.scala` (`countHorizontalMirrored` with `smudges = 1` — it accepts a fold whose mismatch total across all facing pairs lands exactly on the remaining-smudge budget) and p88h/aoc2023 `day13.py` (`find_match_dirty` accepts the fold whose XOR bit count across the fold totals exactly one). The Go oracle reproduced 405 and 400 on the sample with the same mismatch-counting fold.

**Runtime feel.** ~50 ms on the sample. Real patterns run ~20x20 with the fold scan bounded by the shorter side — comfortable in the interpreter.

**Gaps.** No new ticket: the blank-line pattern separators land this day in the exact 2025 day-5 / 2023 day-5 position — the browser `read-line` traps on an empty line before any `catch` could run (#155), and the canonical `error.detail` end-of-file branch the runner must use is itself wasm-fenced (#135), so the door carries the fence note naming `error.detail` exactly as day 5's does (`zhex compile --target=browser` reports the fence; the interpreter run is clean).

## Day 14 — Parabolic Reflector Dish

**Approach.** A tilt is a string rebuild, not a cell shuffle: transpose the grid into column strings, then `_tilt-line` walks a column rebuilding it segment by segment between cube rocks, each segment's rounded rocks packed to its front; a transpose back restores rows. A spin is four tilts with `_rotate` quarter turns between (tilt-north of each rotation covers north, west, south, east). Part 2 never runs its billion spins: `part-two` joins each spun grid into a state key held in a `Map<String, Int>` of first sightings, and the moment a state repeats, `jump` skips whole cycle lengths at once, leaving only the remainder to spin by hand.

**Sample answers.** Part 1 `136`, part 2 `64` (`samples/day14.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day14.scala` (part 2 hashes each spun state into a `Map[String, (Int, Int)]`, and on a repeat adds `(remaining / cycleSize) * cycleSize` iterations in one step before continuing one spin at a time to the target) and p88h/aoc2023 `day14.py` (same seen-state map with a signature string, jumping `remaining // cycle` cycles). The Go oracle reproduced 136 and 64 on the sample with the same map-and-jump loop.

**Runtime feel.** ~70 ms on the sample (its cycle settles in a handful of spins). A real 100x100 platform detects its cycle within a few hundred spins at ~124k interpreted steps each — a run of some seconds to a minute in the interpreter, and the browser-compiled artifact is far faster still.

**Gaps.** None new. One checker lesson for the log, hit twice in one loop: `map.put` hands back the map where `list.append` yields Unit, so a bare `map.put` inside an `if` arm trips the branch-types rule — the house fix (seen in 2025 day 11) is to bind it (`let stored = map.put(...)`) or route the branch through a value-returning `let x = if ... else ...`; both shapes appear in `part-two`. `Map` in the browser subset compiles clean (2025 day 11 already showed that), so no WasmNote.

## Day 15 — Lens Library

**Approach.** The predicted no-char-type trap, met head on: `_code` maps a one-character slice to its code with `text.index-of` against the lowercase and digit alphabets (plus `=` and `-` by hand), and `_hash` is the add-times-17-mod-256 fold over it. Part 2 keeps 256 boxes as `List<List<Lens>>`: a `-` step rebuilds its box without the label (`_without`), an `=` step replaces the label's focal length in place or appends (`_upsert`, one indexed write), and the power sum multiplies box, slot, and focal per lens.

**Sample answers.** Part 1 `1320`, part 2 `145` (`samples/day15.txt`, the public worked example; part 1's value and per-step hashes match the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day15.scala` (256 insertion-ordered maps; `-` removes the label, `=` upserts, power sums `(boxNumber + 1) * (slotNumber + 1) * focalLength`) and p88h/aoc2023 `day15.py` (same boxes-as-lists with a strength map, `(i+1)*(j+1)*strength`). The Go oracle reproduced 1320 and 145 on the sample.

**Runtime feel.** ~50 ms on the sample. The real input's few thousand steps hash in microseconds each — the `index-of` alphabets are constant-size scans — and the box operations are list touches under half a dozen long.

**Gaps.** None new — the char-code trap is the epic's known one (day 1 already paid it for digits; `_code` generalizes the same trick to letters and the two operators, with a `shortcut:` comment naming its grammar limit). The `text.to-int` for focal lengths keeps `part-two` fallible, so its calls carry the postfix `try`. Browser compile succeeds, no WasmNote.

## Day 16 — The Floor Will Be Lava

**Approach.** Directions are ints 0–3 (N, E, S, W) with `_dx`/`_dy` steps, and `_leaving` names the redirect per tile — `/` and `\` index little mapping lists (`[1, 0, 3, 2]` and `[3, 2, 1, 0]`, the day-10 trick of indexing a literal), `|` splits an east/west beam north and south, `-` splits a north/south beam east and west, everything else passes through. `_energized` is the planned iterative worklist, no recursion: a `List<Int>` holds x, y, direction triples consumed by a head index, a `Map<String, Bool>` of seen "x,y,d" states stops a beam repeating itself (each revisit would replay the same splits forever), and a second map keyed "x,y" counts lit tiles by `map.length`. Beams that step off the grid are dropped at consumption by a bounds check — the first draft checked bounds only via `_tile`'s ground fallback, so outside beams walked forever and hit the element limit. Part 2 runs `_energized` from every edge entry heading inward (left column east, right column west, top row south, bottom row north — 2×(width+height) walks) and keeps the maximum.

**Sample answers.** Part 1 `46`, part 2 `51` (`samples/day16.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day16.scala` (`part2` builds the start pairs from every edge tile with its inward direction(s) and takes the max energized count; the test pins 51) and AxlLind/AdventOfCode2023 `src/bin/16.rs` (same edge-entry set — row ends heading in, column ends heading in — mapped over `energized_tiles`, max). ## Day 17 — Clumsy Crucible

**Approach.** Dijkstra over (x, y, direction, run) states exactly as planned: the straight-run limits live in the state, the cost stays pure integer heat. There is no priority-queue word, so the frontier is a `Map<Int, Int>` from packed state to cost and every step min-scans it — samples are small, and the scan is the honest price (logged below). The state packs into one Int (`(x*H+y)*4+direction)*11+run`, run 0–10) so pops decode by division and remainder, no string parsing; `_heat` reads a digit as its index in `"0123456789"`, keeping the walk pure of `text.to-int` Results. The one `_dijkstra` parameterizes both parts: part 1 seeds east/south with run 0 and turns freely up to run 3; part 2 turns only at run ≥ 4, caps run at 10, and accepts the factory cell only with run ≥ 4 behind it.

**Sample answers.** Part 1 `102`, part 2 `94` (`samples/day17.txt`, the public worked example; part 1's value matches the page). The test also pins the page's second part-2 example, the 12×5 detour grid whose ultra-crucible answer is `71`.

**Runtime feel.** ~260 ms on the sample for both parts — the min-scan Dijkstra settles ~2.7k states (part 2's 13×13×4×11) with frontier scans of a few hundred entries each; the op rate is honest map iteration, no indexing trick beyond the packed Int. ## Day 18 — Lavaduct Lagoon

**Approach.** The planned shoelace-plus-Pick walk, all integers: `_area` traces the loop accumulating the cross term `(x + next-x) * (y - next-y)` and the perimeter, then answers `(_abs(cross) + perimeter + 2) / 2` — that numerator is exactly `2*area + boundary + 2`, which Pick's theorem keeps even, so one halving at the end is exact and no floats or halves drift. Directions encode 0–3 as R, D, L, U for both parts, chosen so the hex color's last digit is already the part-2 direction index; `_hex-length` folds the first five hex digits by their place in `"0123456789abcdef"` (`text.index-of`, the day-17 digit trick — no hex parse word exists). `parse` fills one `DigPlan` record with both plans in a single pass; `text.to-int` on the listed distance makes it fallible, so the runner's call site carries the postfix `try`, the day-2 idiom.

**Sample answers.** Part 1 `62`, part 2 `952408144115` (`samples/day18.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2023 `Day18.scala` (`part2` re-parses each color as `Integer.parseInt(color.take(5), 16)` with the last digit indexing `Seq(East, South, West, North)`; the test pins 952408144115) and AxlLind/AdventOfCode2023 `src/bin/18.rs` (splits after `#`, direction `b"RDLU"[last digit]`, distance `isize::from_str_radix(&color[..len-2], 16)`, area by `a += (c + cc) * (r - rr) + n` then `a/2 + 1`). A Go oracle of the absolute-value shoelace reproduced both sample values. One caution for whoever revisits: the example's tenth line color is `#caa171` (last digit 1, D) while the eighth is `#caa173` (3, U) — near-identical colors on two `U 2` lines, and the wrong one leaves the decoded polygon unclosed.

**Runtime feel.** ~50 ms on the sample; the walk is step-count-bound (14 steps), so any real input's few hundred steps land in the same instant — the interpreter never touches per-meter work.

**Gaps.** None new. Known-trap friction only: hex digits via `text.index-of` since there is no char type or hex parse, and the fallible `text.to-int` at the trust boundary handled with `try`. Runner shape unchanged (#134, #135); browser compile succeeds, no WasmNote.

## Day 20 — Pulse Propagation

**Approach.** `parse` keeps the network as parallel lists in one `Network` record — names, kinds (broadcaster / flip-flop / conjunction / untyped output), target lists — then adds undeclared targets as untyped outputs and wires every conjunction's input list; mutable state lives in two `Map<String, Bool>`s (flip-flop on/off, and conjunction memory keyed "module|input"), both mutable through the record binding. `_press` is one FIFO drain with no recursion: three parallel queue lists consumed by a head index, the broadcaster repeats the pulse, flip-flops toggle on low and send their new state, conjunctions update memory then answer low only when every input remembers high. Part 1 folds 1000 presses into the low-times-high product. Part 2 is the input-shape-specialized cycle rule both references use: find the conjunction feeding `rx`, press until each of its inputs has sent it a high pulse, and fold the first-high press numbers with `_lcm` over hand-rolled Euclid `_gcd` (the day-8 pattern). ## Day 24 — Never Tell Me The Odds

**Approach.** The predicted no-float wall, taken exactly: every quantity stays a 64-bit integer. Part 1 intersects each pair's xy paths as rationals kept in numerator/denominator form — future-ness is a sign check, parallel pairs (zero denominator) never cross, and `_axis-in` compares the crossing against the test area in stages: a huge quotient rejects outright, the integer part compares directly, and only the bounded remainder (under |v|) cross-multiplies, so no product leaves the 64-bit range. ## Day 25 — Snowverload

**Approach.** The three wires are a minimum cut of size three, found by max flow: `_reaches` breadth-first searches wires with capacity left, `_flow` pushes up to four edge-disjoint paths from component 0 to each other component, flipping capacities along each path, and the first terminal that stops at three flows sits across the cut — the dry side of the blocked search is one group, everyone else the other. Wires are undirected, so both directions carry capacity one (opposite flows cancel, the trap the Go oracle caught first: single-direction capacities strand half the graph). The finale has no second part, so the door prints the product and then the star, the 2025-day-12 convention.
