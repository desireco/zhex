Runtime traces reachable heap objects and reclaims garbage. This trades CPU and extra heap space for convenient shared lifetimes.

Change the workload

Expand an example to see why a universal speed ranking would mislead.

Sum ten million preallocated integers

There is no need to allocate inside the loop. Generated instructions, vectorization, bounds-check elimination, and memory bandwidth become central. A GC need not be doing significant work on this loop’s behalf.

Create and discard many small objects

Allocation strategy becomes central. Go traces objects; Rust runs destruction and allocator operations; Forth follows the policy you write. Reusing a buffer or resetting a whole region can outperform individual allocations in any suitable implementation.

Wait on a database or network

If external waiting dominates, a faster computation loop may barely change response time. Compare equal concurrency, connection limits, and libraries before attributing differences to the language.

Fit into a small microcontroller

Minimal Forth can be attractive. Rust can also run without its standard library and without a heap. A normal desktop or server Go runtime is a different baseline; specialized Go implementations deserve separate measurement. Embedded Rust documentation.

What a fair benchmark measures

Use the same algorithm, data representation, input, hardware, and correctness requirements. Enable release optimization. Measure throughput, p50/p99 latency, peak resident RAM, allocations, startup time, and executable size separately. Record compiler versions and GC settings.

Compiling Forth is not enough to specify performance: register allocation and stack optimizations matter. Ertl’s implementation study illustrates this; it is not a Go/Rust/Forth benchmark.
