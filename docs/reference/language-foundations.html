Inspect the tradeoffs

BEAM: outsource the most runtime behavior

Start by emitting Erlang source or its supported program representation. Let the existing compiler produce BEAM code. Keep the language's memory and concurrency rules compatible with BEAM. This is the strongest initial fit if actors are central and desktop/server platforms are sufficient.

Compiler interface · Platform packages

JavaScript: TypeScript is an optional intermediate

Emitting TypeScript can help interoperability and inspecting generated programs, but execution uses JavaScript semantics. Browser and server APIs differ. Workers provide parallel execution; an Erlang-style lightweight actor system would need another layer.

TypeScript compilation · Node workers

C: compiling stack code to ordinary expressions works

A checked sequence such as dup multiply can become a function returning x * x. The conceptual stack can disappear. Define numeric behavior explicitly and generate C that preserves it. C compilation does not itself supply memory safety or actor scheduling.

Forth-to-C research · Portable I/O via libuv

Rust: portability without automatically inheriting ownership semantics

Generated safe Rust can validate a useful class of invariants, but the frontend must still define source-language correctness. If arbitrary source programs require unsafe pointers, reference counting or a collector, those costs and responsibilities remain. Target support has different testing tiers.

Rust platform support

Start with one target

Keep parsing and type/stack checking separate from code generation. Choose BEAM for actor-first services, JavaScript when browsers are required, or C for native memory and performance control. Defer another backend until a concrete workload requires it.

Every option still needs testing, deployment work, and a defined set of supported platform/runtime versions. Source portability is different from shipping one executable everywhere.

If WebAssembly is a primary target

Prefer C for one initial backend serving both native and Wasm builds. Consider direct Wasm generation for a Wasm-first language. Both delegate CPU-specific execution to existing tooling, but neither supplies BEAM's actor system.

C → Wasm

Generate C, then use Emscripten for browser integration or a suitable WASI toolchain for supported standalone environments. The same C backend can also feed native compilers. This minimizes new backend engineering while retaining optimization tooling. Emscripten.

Source → Wasm directly

Check types and stack effects, then emit WebAssembly text or binary. Wasm's typed operand stack fits a statically checked stack language, but does not expose Forth's arbitrary data-stack manipulation. Locals handle duplicated or rearranged values. WABT assembles text; Binaryen can optimize output. Wasm execution model · Tools.

Rust → Wasm

A supported route, particularly if Rust libraries or ownership semantics are useful. It adds a Rust translation stage without removing the need to define your language's runtime and host API. Rust Wasm target.

BEAM code inside a Wasm runtime

AtomVM has a WebAssembly port that executes BEAM code. This carries an Erlang-compatible runtime into the Wasm environment; it is a different deployment from directly compiling each application to Wasm. Check feature and library compatibility rather than assuming all Erlang/OTP behavior is available. AtomVM internals.
