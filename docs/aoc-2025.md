# Advent of Code 2025 — findings log

Dogfooding log for solving Advent of Code 2025 in Zhex (epic #123): one section per day, recording the approach, the sample answers, the runtime on the sample input, and the interpreter gaps the day hit — each gap becomes a ticket number. The truth surfaces (`aocSpecs` in `tools/site-data`, ROADMAP) are updated by the stories; this log captures the reasoning in between.

## Day 1 — Secret Entrance

**Approach.** Each input line is `R` or `L` plus a click count; `parse` turns the lines into signed integers (negative for left). The dial runs 0..99 from 50. Part 1 simulates: apply each rotation with a hand-rolled floored mod (`/` and `%` truncate toward zero, so negative wraps fix up by adding the modulus) and count the landings on 0. Part 2 derives each rotation's zero passes in closed form instead of clicking: a right turn ending at the unnormalized spot `landed` crosses `landed / 100` multiples of 100, a left turn `(100 - landed) / 100`, minus one when the turn started on 0; the landing spot then renormalizes.

**Sample answers.** Part 1 `3`, part 2 `6` (`samples/day01.txt`, the public worked example).

**Part 2 sources.** The mechanics are login-gated, so two community references agreed before relying on anything: the HappyCoders walkthrough (happycoders.eu/algorithms/advent-of-code-2025) with its Java repo (SvenWoltmann/advent-of-code-2025, day1 `SecretEntrance.java` — the closed form above) and sanraith/aoc2025 `Day01.h` (click-by-click simulation of the same rule). The sample's part-2 answer came from running both formulations in Go: simulation and closed form both print 6.

**Runtime feel.** Instant on the sample; nothing to measure.

**Gaps.** Two, both ticketed. The one-file idiom the ticket sketched — a day file that runs standalone and is `use`-imported by its test — is impossible because imported files declare words only (#134), so each day is `dayNN.zhex` (runner) plus `dayNN-core.zhex` (importable words). And the documented `error.detail`-based end-of-file branch is fenced in the browser build (#135), so the runner's read loop catches into a sentinel line (`~end-of-input~`) that this day's input alphabet can never contain; `zhex compile --target=browser` then succeeds and the site run panel works.

## Day 2 — Gift Shop

**Approach.** `parse` splits the single input line on commas, then each `first-last` range on its dash, and expands every range into its IDs — the ranges are small enough to enumerate, which is also how the reference solutions stream them. Both parts share `_repeats-block`, which checks whether an ID's digits are the leading block repeated back to back; part 1 accepts only the half-length block (even digit length, two repetitions), part 2 tries every block length from 1 up to half the digit length that divides it evenly.

**Sample answers.** Part 1 `1227775554`, part 2 `4174379265` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `GiftShop.java` (a solver parameterized on the maximum repetition count — unbounded in part 2) and sanraith/aoc2025 `Day02.h` (`hasPattern` tries every dividing block length). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 1227775554, which validates the harness.

**Runtime feel.** ~50 ms on the sample (97 expanded IDs); nothing to optimize.

**Gaps.** None new — the day reuses day 1's runner shape and sentinel read loop (#134, #135).
