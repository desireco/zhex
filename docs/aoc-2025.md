# Advent of Code 2025 — findings log

Dogfooding log for solving Advent of Code 2025 in Zhex (epic #123): one section per day, recording the approach, the sample answers, the runtime on the sample input, and the interpreter gaps the day hit — each gap becomes a ticket number. The truth surfaces (`aocSpecs` in `tools/site-data`, ROADMAP) are updated by the stories; this log captures the reasoning in between.

## Day 1 — Secret Entrance

**Approach.** Each input line is `R` or `L` plus a click count; `parse` turns the lines into signed integers (negative for left). The dial runs 0..99 from 50. Part 1 simulates: apply each rotation with a hand-rolled floored mod (`/` and `%` truncate toward zero, so negative wraps fix up by adding the modulus) and count the landings on 0. Part 2 derives each rotation's zero passes in closed form instead of clicking: a right turn ending at the unnormalized spot `landed` crosses `landed / 100` multiples of 100, a left turn `(100 - landed) / 100`, minus one when the turn started on 0; the landing spot then renormalizes.

**Sample answers.** Part 1 `3`, part 2 `6` (`samples/day01.txt`, the public worked example).

**Part 2 sources.** The mechanics are login-gated, so two community references agreed before relying on anything: the HappyCoders walkthrough (happycoders.eu/algorithms/advent-of-code-2025) with its Java repo (SvenWoltmann/advent-of-code-2025, day1 `SecretEntrance.java` — the closed form above) and sanraith/aoc2025 `Day01.h` (click-by-click simulation of the same rule). The sample's part-2 answer came from running both formulations in Go: simulation and closed form both print 6.

**Runtime feel.** Instant on the sample; nothing to measure.

**Gaps.** Two, both ticketed. The one-file idiom the ticket sketched — a day file that runs standalone and is `use`-imported by its test — is impossible because imported files declare words only (#134), so each day is `dayNN.zhex` (runner) plus `dayNN-core.zhex` (importable words). And the documented `error.detail`-based end-of-file branch is fenced in the browser build (#135), so the runner's read loop catches into a sentinel line (`~end-of-input~`) that this day's input alphabet can never contain; `zhex compile --target=browser` then succeeds and the site run panel works.

## Day 2 — Gift Shop

**Approach.** `parse` splits the single input line on commas, then each `first-last` range on its dash, and expands every range into its IDs — the ranges are small enough to enumerate, which is also how the reference solutions stream them. Both parts share `_repeats-block`, which checks whether an ID's digits are the leading block repeated back to back; part 1 accepts only the half-length block (even digit length, two repetitions), part 2 tries every block length from 1 up to half the digit length that divides it evenly.

**Sample answers.** Part 1 `1227775554`, part 2 `4174379265` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `GiftShop.java` (a solver parameterized on the maximum repetition count — unbounded in part 2) and sanraith/aoc2025 `Day02.h` (`hasPattern` tries every dividing block length). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 1227775554, which validates the harness.

**Runtime feel.** ~50 ms on the sample (97 expanded IDs); nothing to optimize.

**Gaps.** None new — the day reuses day 1's runner shape and sentinel read loop (#134, #135).

## Day 3 — Lobby

**Approach.** `parse` turns each line into its list of digit integers (there is no char type, so each battery is a one-character `text.slice` through `text.to-int`, done once at the boundary so the greedy stays pure). Both parts share `_best-output`: for each of the number's digits, scan the window that still leaves room for the remaining picks, take its largest digit (first occurrence on ties), and continue after it. Part 1 picks two digits per bank, part 2 twelve; each part sums the banks' outputs.

**Sample answers.** Part 1 `357`, part 2 `3121910778619` (`samples/day03.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Lobby.java`/`LobbyMain.java` (the same solver parameterized on batteries per bank — 2 then 12) and sanraith/aoc2025 `Day03.h` (`calculateTotalJoltage(parse(input), 12)` with the same shrinking-window greedy). The part-2 sample value came from a Go implementation of that greedy; the same run reproduced part 1's published 357.

**Runtime feel.** ~50 ms on the sample; the twelve-digit pass barely differs from the two-digit one.

**Gaps.** The digit handling is the expected no-char-type friction (one-character slices plus `text.to-int`), already on the epic's known-traps list, so no new ticket. Runner shape unchanged (#134, #135).

## Day 4 — Printing Department

**Approach.** The grid stays a list of row strings; `_occupied` bounds-checks a cell and `_neighbor-count` scans the eight neighbors. Part 1 counts the `@` cells with fewer than four occupied neighbors. Part 2 repeats simultaneous removal rounds — `_remove-round` rebuilds each row with accessible rolls replaced by `.`, reading neighbor counts from the round's starting grid so every removal in a round is decided at once — until a round removes nothing, summing every removed roll. Iteration, not recursion, so the 256-deep call limit never comes near.

**Sample answers.** Part 1 `13`, part 2 `43` (`samples/day04.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `PrintingDepartment.java` (`solve(input, repeatUntilNoMore)` — find accessible rolls, remove them all, repeat) and sanraith/aoc2025 `Day04.h` (the same collect-erase loop counting each removed roll). The part-2 sample value came from a Go implementation of the simultaneous-round rule; the same run reproduced part 1's published 13.

**Runtime feel.** ~70 ms on the sample (a handful of fixpoint rounds over a 10x10 grid); nothing to measure yet — the epic's perf worries start at day 9's scale.

**Gaps.** None new. String rows rebuild by `+` concatenation each round (quadratic in row length in theory, irrelevant at these sizes); a mutable grid word would matter only for the big-grid days. Runner shape unchanged (#134, #135).

## Day 5 — Cafeteria

**Approach.** `parse` walks the lines, flips from ranges to IDs at the first blank line, and splits each range on its dash into an `IdRange` record; the whole database lands in one `Database` record. Part 1 counts the available IDs covered by any range (`list.any` with a partial `_covers(_, id)`). Part 2 measures the union of the ranges without a set type: sort the ranges by first ID (`list.sort-by` with a key word), then sweep — a range overlapping the current span extends it, a range past its end closes the span and opens a new one — summing each span's length so overlaps count once.

**Sample answers.** Part 1 `3`, part 2 `14` (`samples/day05.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Cafeteria.java` (`RangeSet` merges the ranges, part 2 sums the merged sizes and ignores the available IDs) and sanraith/aoc2025 `Day05.h` (sorts ranges, adds each range's length minus the overlap with the running end). The part-2 sample value came from a Go implementation of the sweep; the same run reproduced part 1's published 3.

**Runtime feel.** ~60 ms on the sample; nothing to measure.

**Gaps.** None new. The sort-and-merge sweep is the epic's planned stand-in for a set type; no ticket needed. Runner shape unchanged (#134, #135).

## Day 6 — Trash Compactor

**Approach.** `parse` decodes the whole worksheet into a `Worksheet` record: the operator row's non-space characters give the problems' operators, the row-wise reading (part 1) splits each data row's non-space fields into one number per problem in order, and the column-wise reading (part 2) stacks each column's digits top to bottom into one number, advancing to the next problem at each all-space column — there is no char type, so every cell is a one-character `text.slice` and digits become numbers once at this boundary. Both parts are then the same pure fold: apply each problem's `+` or `*` to its numbers and total the answers.

**Sample answers.** Part 1 `4277556`, part 2 `3263827` (`samples/day06.txt`, the public worked example with its trailing spaces preserved; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `WorksheetParser.java` (`readNumbersInColumns` — a column of digits top to bottom is one number, a zero column advances the problem index) and sanraith/aoc2025 `Day06.h` (operators anchor position ranges; each problem owns the columns up to the next operator). The part-2 sample value came from a Go implementation of the column stacking; the same run reproduced part 1's published 4277556.

**Runtime feel.** ~60 ms on the sample; the column pass is one sweep over a 4x15 worksheet.

**Gaps.** None new — the no-char-type friction is the epic's known trap (one-character slices plus `text.to-int`, like day 3). Runner shape unchanged (#134, #135).

## Day 7 — Laboratories

**Approach.** One additive DP answers both parts, no recursion and no beam queue: a `List<Int>` holds how many beam timelines enter the current row at each column (1 at the entry's column below `S`). `_advance` walks a row: a timeline on open space continues down, a timeline on a splitter moves to the splitter's left and right neighbors (both kept when they land together — the counts add), so each row is one pass. Part 1 counts the splitter cells the entering beam array marks as reached (each splitter splits at most once because beams only move down); part 2 sums the timeline counts that leave the bottom row.

**Sample answers.** Part 1 `21`, part 2 `40` (`samples/day07.txt`, the public worked example; part 1's value matches the page — 22 splitters stand, one is never reached).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Laboratories.java` (`solve(input, countTachyons)` — the same row DP, part 2 returns the sum of the final tachyon array) and sanraith/aoc2025 `Day07.h` (`countPaths` memoizes distinct paths from each cell to the bottom). The part-2 sample value came from a Go implementation of the row DP; the same run reproduced part 1's published 21.

**Runtime feel.** ~80 ms on the sample (15 rows of 15 columns); the counts stay small, so Int64 headroom is enormous.

**Gaps.** None new. The epic's Pascal-like-growth worry is about the real input's width, not the sample; the door runs the sample. Runner shape unchanged (#134, #135).

## Day 8 — Playground

**Integrality check (the ticket's first step).** Passed: distances order pairs and never become output. Both references sort the candidate pairs by straight-line distance and then only iterate that order; squared integer distance gives exactly the same order (square root is monotonic), and it keeps equal-distance ties exact instead of rounding them into false ties. Part 2's answer is the product of the completing pair's X coordinates — pure Int. Squared distances fit Int64 with huge headroom (coordinates are three digits in the example, low thousands in the real list). No floats, no gap ticket.

**Approach.** `parse` splits each `X,Y,Z` line into a `Box` record. `_connections` enumerates every box pair once as a `Connection` record ranked by squared distance and sorts them ascending (`list.sort-by`, stable on ties). Circuits live in two maps: an owner map (box index to circuit id) and a members map (circuit id to its member list); `_connect` joins two boxes' circuits, merging the smaller member list into the larger and reassigning owners — union-find without trees. Part 1 makes the given number of closest connections and multiplies the sizes of the three largest circuits left in the members map. Part 2 connects pairs in ascending order until one circuit remains, answering with the completing pair's X-coordinate product. The runner passes 1000 connections for a full list and the example's 10 for the 20-box sample (the puzzle fixes both numbers; the door runs the sample).

**Sample answers.** Part 1 `40`, part 2 `25272` (`samples/day08.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Playground.java` (`solvePart2` connects sorted pairs until `circuits.size() == 1`, then returns `first.x() * second.x()`) and sanraith/aoc2025 `Day08.h` (the same sorted-pair union-find, `lastPair.first.x * lastPair.second.x`). The part-2 sample value came from a Go implementation using squared integer distances; the same run reproduced part 1's published 40 with ten connections.

**Runtime feel.** ~80 ms on the sample (190 pairs over 20 boxes). The real 1000-box list would push 49,950 pairs through the interpreter's sort — the door runs the sample, and the epic defers real-input perf to V1.

**Gaps.** None new. The `Map`-based union-find and `sort-by` ranking are exactly the epic's planned stand-ins (no set type, no floats needed). Runner shape unchanged (#134, #135).
