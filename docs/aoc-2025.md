# Advent of Code 2025 — findings log

Dogfooding log for solving Advent of Code 2025 in Zhex (epic #123): one section per day, recording the approach, the sample answers, the runtime on the sample input, and the interpreter gaps the day hit — each gap becomes a ticket number. The truth surfaces (`aocSpecs` in `tools/site-data`, ROADMAP) are updated by the stories; this log captures the reasoning in between.

## Day 1 — Secret Entrance

**Approach.** Each input line is `R` or `L` plus a click count; `parse` turns the lines into signed integers (negative for left). The dial runs 0..99 from 50. Part 1 simulates: apply each rotation with a hand-rolled floored mod (`/` and `%` truncate toward zero, so negative wraps fix up by adding the modulus) and count the landings on 0. Part 2 derives each rotation's zero passes in closed form instead of clicking: a right turn ending at the unnormalized spot `landed` crosses `landed / 100` multiples of 100, a left turn `(100 - landed) / 100`, minus one when the turn started on 0; the landing spot then renormalizes.

**Sample answers.** Part 1 `3`, part 2 `6` (`samples/day01.txt`, the public worked example).

**Part 2 sources.** The mechanics are login-gated, so two community references agreed before relying on anything: the HappyCoders walkthrough (happycoders.eu/algorithms/advent-of-code-2025) with its Java repo (SvenWoltmann/advent-of-code-2025, day1 `SecretEntrance.java` — the closed form above) and sanraith/aoc2025 `Day01.h` (click-by-click simulation of the same rule). The sample's part-2 answer came from running both formulations in Go: simulation and closed form both print 6.

**Runtime feel.** Instant on the sample; nothing to measure.

**Gaps.** Two, both ticketed. The one-file idiom the ticket sketched — a day file that runs standalone and is `use`-imported by its test — is impossible because imported files declare words only (#134), so each day is `dayNN.zhex` (runner) plus `dayNN-core.zhex` (importable words). And the documented `error.detail`-based end-of-file branch is fenced in the browser build (#135), so the runner's read loop catches into a sentinel line (`~end-of-input~`) that this day's input alphabet can never contain; `zhex compile --target=browser` then succeeds and the site run panel works.

## Day 2 — Gift Shop

**Approach.** `parse` splits the single input line on commas, then each `first-last` range on its dash, and expands every range into its IDs — the ranges are small enough to enumerate, which is also how the reference solutions stream them. Both parts share `_repeats-block`, which checks whether an ID's digits are the leading block repeated back to back; part 1 accepts only the half-length block (even digit length, two repetitions), part 2 tries every block length from 1 up to half the digit length that divides it evenly.

**Sample answers.** Part 1 `1227775554`, part 2 `4174379265` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `GiftShop.java` (a solver parameterized on the maximum repetition count — unbounded in part 2) and sanraith/aoc2025 `Day02.h` (`hasPattern` tries every dividing block length). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 1227775554, which validates the harness.

**Runtime feel.** ~50 ms on the sample (97 expanded IDs); nothing to optimize.

**Gaps.** None new — the day reuses day 1's runner shape and sentinel read loop (#134, #135).

## Day 3 — Lobby

**Approach.** `parse` turns each line into its list of digit integers (there is no char type, so each battery is a one-character `text.slice` through `text.to-int`, done once at the boundary so the greedy stays pure). Both parts share `_best-output`: for each of the number's digits, scan the window that still leaves room for the remaining picks, take its largest digit (first occurrence on ties), and continue after it. Part 1 picks two digits per bank, part 2 twelve; each part sums the banks' outputs.

**Sample answers.** Part 1 `357`, part 2 `3121910778619` (`samples/day03.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Lobby.java`/`LobbyMain.java` (the same solver parameterized on batteries per bank — 2 then 12) and sanraith/aoc2025 `Day03.h` (`calculateTotalJoltage(parse(input), 12)` with the same shrinking-window greedy). The part-2 sample value came from a Go implementation of that greedy; the same run reproduced part 1's published 357.

**Runtime feel.** ~50 ms on the sample; the twelve-digit pass barely differs from the two-digit one.

**Gaps.** The digit handling is the expected no-char-type friction (one-character slices plus `text.to-int`), already on the epic's known-traps list, so no new ticket. Runner shape unchanged (#134, #135).

## Day 4 — Printing Department

**Approach.** The grid stays a list of row strings; `_occupied` bounds-checks a cell and `_neighbor-count` scans the eight neighbors. Part 1 counts the `@` cells with fewer than four occupied neighbors. Part 2 repeats simultaneous removal rounds — `_remove-round` rebuilds each row with accessible rolls replaced by `.`, reading neighbor counts from the round's starting grid so every removal in a round is decided at once — until a round removes nothing, summing every removed roll. Iteration, not recursion, so the 256-deep call limit never comes near.

**Sample answers.** Part 1 `13`, part 2 `43` (`samples/day04.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `PrintingDepartment.java` (`solve(input, repeatUntilNoMore)` — find accessible rolls, remove them all, repeat) and sanraith/aoc2025 `Day04.h` (the same collect-erase loop counting each removed roll). The part-2 sample value came from a Go implementation of the simultaneous-round rule; the same run reproduced part 1's published 13.

**Runtime feel.** ~70 ms on the sample (a handful of fixpoint rounds over a 10x10 grid); nothing to measure yet — the epic's perf worries start at day 9's scale.

**Gaps.** None new. String rows rebuild by `+` concatenation each round (quadratic in row length in theory, irrelevant at these sizes); a mutable grid word would matter only for the big-grid days. Runner shape unchanged (#134, #135).

## Day 5 — Cafeteria

**Approach.** `parse` walks the lines, flips from ranges to IDs at the first blank line, and splits each range on its dash into an `IdRange` record; the whole database lands in one `Database` record. Part 1 counts the available IDs covered by any range (`list.any` with a partial `_covers(_, id)`). Part 2 measures the union of the ranges without a set type: sort the ranges by first ID (`list.sort-by` with a key word), then sweep — a range overlapping the current span extends it, a range past its end closes the span and opens a new one — summing each span's length so overlaps count once.

**Sample answers.** Part 1 `3`, part 2 `14` (`samples/day05.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Cafeteria.java` (`RangeSet` merges the ranges, part 2 sums the merged sizes and ignores the available IDs) and sanraith/aoc2025 `Day05.h` (sorts ranges, adds each range's length minus the overlap with the running end). The part-2 sample value came from a Go implementation of the sweep; the same run reproduced part 1's published 3.

**Runtime feel.** ~60 ms on the sample; nothing to measure.

**Gaps.** One new, ticketed as #155: the browser build's `read-line` traps with a native out-of-bounds when the next input line is empty, so no browser-compiled program can read this day's blank section separator — the Go interpreter reads it fine, and the sentinel workaround from days 1-4 cannot dodge a trap that fires before any `catch` runs. The runner therefore uses the canonical `error.detail` end-of-file branch, which #135 already fences, and the door carries the fence note naming `error.detail` instead of a run panel — an honest door, not a fake one. The sort-and-merge sweep itself is the epic's planned stand-in for a set type; no ticket needed there.

## Day 6 — Trash Compactor

**Approach.** `parse` decodes the whole worksheet into a `Worksheet` record: the operator row's non-space characters give the problems' operators, the row-wise reading (part 1) splits each data row's non-space fields into one number per problem in order, and the column-wise reading (part 2) stacks each column's digits top to bottom into one number, advancing to the next problem at each all-space column — there is no char type, so every cell is a one-character `text.slice` and digits become numbers once at this boundary. Both parts are then the same pure fold: apply each problem's `+` or `*` to its numbers and total the answers.

**Sample answers.** Part 1 `4277556`, part 2 `3263827` (`samples/day06.txt`, the public worked example with its trailing spaces preserved; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `WorksheetParser.java` (`readNumbersInColumns` — a column of digits top to bottom is one number, a zero column advances the problem index) and sanraith/aoc2025 `Day06.h` (operators anchor position ranges; each problem owns the columns up to the next operator). The part-2 sample value came from a Go implementation of the column stacking; the same run reproduced part 1's published 4277556.

**Runtime feel.** ~60 ms on the sample; the column pass is one sweep over a 4x15 worksheet.

**Gaps.** None new — the no-char-type friction is the epic's known trap (one-character slices plus `text.to-int`, like day 3). Runner shape unchanged (#134, #135).

## Day 7 — Laboratories

**Approach.** One additive DP answers both parts, no recursion and no beam queue: a `List<Int>` holds how many beam timelines enter the current row at each column (1 at the entry's column below `S`). `_advance` walks a row: a timeline on open space continues down, a timeline on a splitter moves to the splitter's left and right neighbors (both kept when they land together — the counts add), so each row is one pass. Part 1 counts the splitter cells the entering beam array marks as reached (each splitter splits at most once because beams only move down); part 2 sums the timeline counts that leave the bottom row.

**Sample answers.** Part 1 `21`, part 2 `40` (`samples/day07.txt`, the public worked example; part 1's value matches the page — 22 splitters stand, one is never reached).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Laboratories.java` (`solve(input, countTachyons)` — the same row DP, part 2 returns the sum of the final tachyon array) and sanraith/aoc2025 `Day07.h` (`countPaths` memoizes distinct paths from each cell to the bottom). The part-2 sample value came from a Go implementation of the row DP; the same run reproduced part 1's published 21.

**Runtime feel.** ~80 ms on the sample (15 rows of 15 columns); the counts stay small, so Int64 headroom is enormous.

**Gaps.** None new. The epic's Pascal-like-growth worry is about the real input's width, not the sample; the door runs the sample. Runner shape unchanged (#134, #135).

## Day 8 — Playground

**Integrality check (the ticket's first step).** Passed: distances order pairs and never become output. Both references sort the candidate pairs by straight-line distance and then only iterate that order; squared integer distance gives exactly the same order (square root is monotonic), and it keeps equal-distance ties exact instead of rounding them into false ties. Part 2's answer is the product of the completing pair's X coordinates — pure Int. Squared distances fit Int64 with huge headroom (coordinates are three digits in the example, low thousands in the real list). No floats, no gap ticket.

**Approach.** `parse` splits each `X,Y,Z` line into a `Box` record. `_connections` enumerates every box pair once as a `Connection` record ranked by squared distance and sorts them ascending (`list.sort-by`, stable on ties). Circuits live in two maps: an owner map (box index to circuit id) and a members map (circuit id to its member list); `_connect` joins two boxes' circuits, merging the smaller member list into the larger and reassigning owners — union-find without trees. Part 1 makes the given number of closest connections and multiplies the sizes of the three largest circuits left in the members map. Part 2 connects pairs in ascending order until one circuit remains, answering with the completing pair's X-coordinate product. The runner passes 1000 connections for a full list and the example's 10 for the 20-box sample (the puzzle fixes both numbers; the door runs the sample).

**Sample answers.** Part 1 `40`, part 2 `25272` (`samples/day08.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: HappyCoders' walkthrough plus its Java `Playground.java` (`solvePart2` connects sorted pairs until `circuits.size() == 1`, then returns `first.x() * second.x()`) and sanraith/aoc2025 `Day08.h` (the same sorted-pair union-find, `lastPair.first.x * lastPair.second.x`). The part-2 sample value came from a Go implementation using squared integer distances; the same run reproduced part 1's published 40 with ten connections.

**Runtime feel.** ~80 ms on the sample (190 pairs over 20 boxes). The real 1000-box list would push 49,950 pairs through the interpreter's sort — the door runs the sample, and the epic defers real-input perf to V1.

**Gaps.** None new. The `Map`-based union-find and `sort-by` ranking are exactly the epic's planned stand-ins (no set type, no floats needed). Runner shape unchanged (#134, #135).

## Day 9 — Movie Theater

**Approach.** The input lists the red tiles one `x,y` pair per line, and — the part-2 revelation — in input order they walk a closed orthogonal loop: consecutive tiles share a row or a column, and the last connects back to the first. Part 1 is the plain pair scan: every two red tiles are opposite corners of a candidate rectangle counted inclusively, `(dx+1)*(dy+1)`, take the maximum (the optimum needs no cleverness — 496 tiles in the real input, 28 pairs in the sample). Part 2 must not lay new tiles outside the loop: compress coordinates first (the grid spans ~100,000 by ~100,000 but only the red tiles' distinct xs and ys matter, so sort-and-dedupe each axis into a compressed index), draw the loop's border into a compressed grid holding one margin ring, flood-fill the outside from the corner of that ring with an explicit `List` used as a stack (the 256 word-call depth limit forbids recursive fill), then rescan the pairs: a rectangle whose inclusive compressed footprint contains no outside cell is valid, its area still computed from original coordinates; a rectangle of original width or height 1 is valid outright because the tiles between two red tiles on one line are the loop's own green tiles. Iteration only — two nested `for` loops per stage, one `while` for the fill; recursion nowhere.

**Sample answers.** Part 1 `50` (the public page's worked example), part 2 `24`.

**Sources.** The public page states part 1 and pins 50; part 2 is login-gated, so two community references agreed the mechanics: HappyCoders' walkthrough plus its Java `MovieTheater.java`/`TileFloor.java` (compression to sorted distinct coordinates, margin ring, flood fill of the outside, original-coordinate area) and sanraith/aoc2025 `Day09.h` (the same containment rule checked via lines one tile inside each edge). HappyCoders' `MovieTheaterTest` pins the sample's part 2 at 24; a Go oracle implementing the agreed rule reproduced both 50 and 24.

**Runtime feel.** ~50 ms on the sample (8 tiles; the compressed grid is 6x6 and the fill touches a few dozen cells). The real input's 496 tiles mean ~123k pair scans over a ~250x250 compressed footprint — minutes in this interpreter, a real-input-only cost and a finding, not a sample failure.

**Gaps.** One expected, already on the epic's trap list: no list word pops, so the flood fill's explicit stack keeps a live-size counter and overwrites popped slots in place (four repeated three-line pushes in `_flood-outside`). Recorded here; ticketed only if later days hit the same wall harder. The browser build compiles the day clean — `console.fail` is fenced in it (#noted in the B1 sentinel pattern), so the core has no guard branch and trusts the input contract that consecutive loop tiles share a row or column, which both references confirm every valid input satisfies.

## Day 10 — Factory

**Approach.** Each line is one machine: a light diagram in brackets (the target pattern, machines start dark), button wirings in parentheses (the 0-based light indices each press flips), and joltage numbers in braces. Part 1 presses buttons least: pressing a button twice reverts it, so every button is pressed zero or one times and the reachable states are subsets — a breadth-first search from all-off over encoded states (a light pattern becomes one Int by place value, `value = value * 2 + on`, at most 13 lights so 8192 states; visited is a `List<Bool>` indexed by that encoding, and a press toggles a light arithmetically — add or subtract its place value depending on the digit read off by `/` and `%`, since the language has no bitwise words). The queue is a plain `List` plus a head counter (no pop word, so nothing ever leaves the list; it only grows to at most the state count). Part 2 gives the joltages their meaning: each light must be toggled exactly as many times as its joltage number, so the press counts x satisfy one equation per light — the sum of the x of every button toggling that light equals its joltage — and the answer per machine minimizes the total presses over non-negative integer solutions. That is searched, not solved symbolically: buttons in order, each press count from 0 up to the smallest joltage among its lights (farther would go negative), mutating a remaining-joltage list and restoring it on backtrack, pruning any branch already at or past the best total, and accepting only assignments that land every remainder on exactly zero. The recursion bottoms out at button count plus one — at most 14 nested calls, nowhere near the 256 limit.

**Sample answers.** Part 1 `7` (the public page's worked example: 2 + 3 + 2 presses), part 2 `33` (10 + 12 + 11).

**Sources.** The public page states part 1 and pins 7; part 2 is login-gated, so two community references agreed the mechanics: HappyCoders' walkthrough plus its Java `Machine.java`/`GaussianElimination.java` (press frequencies as unknowns, one equation per light, minimize the sum, solutions enumerated to at most three free unknowns) and sanraith/aoc2025 `Day10.h` (backtracking over per-button press counts bounded by the minimum joltage they touch, success only when the remainder is exactly zero). A Go oracle implementing the agreed rule reproduced the page's 7 and, independently of the hand algebra over the three sample machines (10 + 12 + 11), printed 33.

**Runtime feel.** ~160 ms on the sample (three machines; the part 1 BFS visits a few dozen of each machine's ≤8192 states, the part 2 search a few thousand count assignments with the running-total prune).

**Gaps.** No new wall: the encoded-state BFS dodges the missing bitwise words by place-value arithmetic, and the queue's append-only head index works around the missing pop the same way day 9's stack did — the no-set/no-stack theme from the epic's trap list, absorbed rather than ticketed. Part 2's search carries no per-light reachability prune (remaining joltage versus what later buttons can still deliver), so a real input with many loosely constrained buttons would crawl; a sample-scale note, not a sample failure.

## Day 11 — Reactor

**Approach.** The input is a wiring list — each line names a device and the devices its outputs feed — and data only flows forward, so the wiring is a DAG. Part 1 counts the distinct routes from `you` to `out`. No recursion and no depth-first anything: the count accumulates over a topological order built by Kahn's algorithm (count each device's incoming wires, queue the sources, dequeue a device, push its path count to its targets, a target with no incoming wires left joins the queue) — a plain append-only list walked by a head index again. `ways[you]` starts at 1, every wire u→v does `ways[v] += ways[u]`, and the answer reads `ways[out]` through a `Map<String, Int>` whose absent keys mean zero. Part 2 restarts from a new device `svr` and counts only the routes that visit both `dac` and `fft`; instead of threading two seen-flags through the accumulation (the references' memoized trick), the same counting word runs four times with nodes deleted — all routes minus routes avoiding `dac` minus routes avoiding `fft` plus routes avoiding both — inclusion-exclusion over four ordinary path counts, each iterative topological accumulation. Word-call depth never exceeds two.

**Sample answers.** Part 1 `5`, part 2 `2`. The day's two parts ship two different public examples: the page's example (`aaa: you hhh` …) pins part 1 at 5, and the part-2 example (`svr: aaa bbb` …) pins part 2 at 2. The sample file is the part-1 example per the arc's convention, so the door's part-2 answer reads `0` there — `svr` is simply absent from that wiring; the test file checks both examples and pins that 0 too.

**Sources.** The public page states part 1 and pins 5. Part 2 is login-gated; two community references agreed the mechanics: HappyCoders' `Reactor.java` plus its `ReactorTest` (start `svr`, count routes that saw both `dac` and `fft`, sample pinned at 2 — its own second example input) and sanraith/aoc2025 `Day11.h` (the same start and both-nodes flag condition). A Go oracle counting by Kahn accumulation and inclusion-exclusion reproduced 5 and 2 — agreeing with both references' own pinned values.

**Runtime feel.** ~50 ms on the sample (ten devices; four Kahn passes each for part 2).

**Gaps.** A small checker-law stumble worth recording: `map.put` passes the map through as its value, so a `map.put` in a branch-final position makes the branch's type the map instead of Unit — the discard idiom is `let updated = map.put(...)`, which the interpreter's own map tests sanction. No new ticket: law, not friction. The door's part-2 answer reads `0` because the sample file is part one's example and `svr` is absent from it — the test file pins both examples' answers (5, 2) plus that 0, and the site row carries ["5", "0"] honestly.

## Day 12 — Christmas Tree Farm

**Approach.** The input has two sections: six present shapes as small `#`/`.` grids, then one line per tree region — `12x5: 1 0 1 0 3 2` is a region twelve wide, five long, wanting one present of shape 0, one of shape 2, three of shape 4, two of shape 5. Presents sit on the grid, may rotate and flip, may not overlap or stack, and their `.` holes interlock around other presents. Part 1 counts the regions that fit everything. Two published filters come first: the presents' `#`-cell total against the region's cell count, then HappyCoders' slot count `(width / max-shape-width) * (height / max-shape-height)` — that many presents always fit. When both abstain, the packer runs — and the packer is where this day earned its HIGH badge: the sample's third region passes both filters (49 cells wanted in 60) yet cannot be packed, and no row-counting argument proves it (a per-row profile assignment with exactly the 11 holes exists), so the impossibility is genuinely geometric. Three search formulations were measured in Go before any Zhex was written: free-anchor backtracking (245 million nodes), first-`#`-pinned enumeration with a hole budget (15 million), most-stuck-present-first ordering (71 million on the impossible region — though only 2,610 on the satisfiable one). All are far beyond this interpreter's ~10 million operations per second. What survived is a column-sweep dynamic program: sweep anchor columns left to right; a state is the pending coverage of the window the shapes still reach (bits as place values — no bitwise words) plus the remaining per-shape counts packed three bits each into one Int state key in a `Map<Int, Bool>` frontier; filling a column recursively tries every non-overlapping set of presents anchored there and emits each reachable successor, so every distinct partial configuration is paid for once instead of once per path. The three sample regions cost 15, 5,543 and 10,732 states — about 46,000 column fills in total. Recursion depth is the presents-per-column bound plus one, single digits. Part 2 is the twelve-day event's finale, not an algorithm: with every star collected it asks nothing further, and the community's customary completion answer is the star itself — the runner prints `*`, as three independent published solutions also do.

**Sample answers.** Part 1 `2` (the public page's worked example — regions one and two fit, three does not), part 2 `*` (the finale's customary answer).

**Sources.** The public page states part 1, carries the full six-shape example, and pins 2. Part 2 is login-gated: HappyCoders' `Tree.java`/`Present.java`/`Shape.java` plus its `ChristmasTreeFarmTest` (the sample input verbatim, answer 2, the two-filter-then-search shape, and the note that the real input never reaches the search) agreed with the community record — the tildes day-12 thread and hamatti's walkthrough (the real input needs only the area check; part 2 solutions print `*` or zero, e.g. Thecakeisalime's `return '*'` and Berdes' no-op). A Go oracle implementing the filters-plus-search rule reproduced the page's 2 — including rejecting the third region, which the filters alone would have accepted; the same oracle family measured the three rejected search formulations and the column-sweep DP's state counts before any Zhex landed.

**Runtime feel.** ~9 s on the sample (all three regions reach the packer; the DP's ~46,000 column fills dominate). The real input is expected to decide almost every region at the filters, per both references — but any region that reaches the packer with height over 14 overflows the state key (see the shortcut note in `_region-packs`), a real-input-only cliff recorded here, not hit by the sample.

**Gaps.** The big one, ticketed (#159): this interpreter has no set, stack, or pop words and no bitwise operations, and the packing DP had to encode occupancy masks as place-value Ints tested with `/` and `%`, build stacks as append-only lists walked by head counters, and hash states into `Map<Int, Bool>` by hand — every one of the epic's predicted friction points hit on the same day. The 9-second sample time is the interpreter's raw op rate, not an algorithm problem; the browser build of the same program answers in 80 milliseconds (the wasm engine is that much faster than the tree-walking interpreter — itself a finding). Lesser notes: a multi-line arithmetic expression cannot continue after a trailing operator (found day 11, hit again day 12), and the shape transforms must re-sort their cells so the row-major first `#` stays well defined — one `list.sort` each, absorbed.

**Engine bug found and fixed.** Day 12's sample is the first stdin in the corpus with blank lines, and the browser engine's `read-line` trapped on every one of them: the `\r` chomp guarded its `array.get` at index `length - 1` with `i32.and`, which evaluates both arms — a zero-length line read the byte at index -1. Fixed with nested `if`s in `internal/lang/watprelude_m3.go` (the same latent pattern in the json number-literal check fixed the same way), pinned by a new differential fixture `readline-blank` (`Ada\n\nGrace\n`) in `internal/wasm/compile_test.go`. Days 5-8's samples with blank lines inherit the fix.
