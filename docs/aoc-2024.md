## Day 1 — Historian Hysteria

**Approach.** `parse` splits each line on its single space into the two columns, held in one `Lists` record. Part 1 sorts both columns (`list.sort` returns sorted copies) and totals the rank-by-rank distances, negating the difference when the left value is smaller — there is no `abs` word. Part 2 counts the right column into a `Map<Int, Int>` (the `_seen` helper turns the `Option` read into a plain count), then totals each left ID times its count.

**Sample answers.** Part 1 `11`, part 2 `31` (`samples/day01.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day01.py` (`sum(x * _right.count(x) for x in _left)`) and timvisee/advent-of-code-2024 `day01b/src/main.rs` (a counting array indexed by the right IDs, each left ID multiplied by its entry). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 11. The Observable walkthrough (observablehq.com/d/a87155f309efaf26) independently states 31 for the same lists.

**Runtime feel.** Instant on the sample; nothing to measure.

**Gaps.** None new — the runner reuses the 2025 sentinel read loop (#134, #135) and the day compiles to the browser subset, so the door gets its run panel.

## Day 2 — Red-Nosed Reports

**Approach.** `parse` splits each line on spaces into one `List<Int>` per report. `_safe` walks the steps once, tracking whether any step breaks the increasing run, the decreasing run, or the 1..3 bound; a report passes when one direction survives and the bound holds — a zero step kills both directions, so equal neighbors stay unsafe. Part 1 counts the safe reports. Part 2 retries each report with one level removed (`_without` rebuilds the row), accepting the report when any removal is safe; the retry loop stops at the first tolerated removal.

**Sample answers.** Part 1 `2`, part 2 `4` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day02.py` (tries every single-level removal) and timvisee/advent-of-code-2024 `day02b/src/main.rs` (`(0..nums.len()).any(|i| ...)` over each removal with the same direction-and-bound fold). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 2.

**Runtime feel.** Instant on the sample (six five-level reports, at most five removals each).

**Gaps.** None new — the removal trial is plain loops; the day stays in the browser subset and keeps the run panel.

## Day 3 — Mull It Over

**Approach.** There is no regex, so both parts scan by `text.index-of` over a shrinking remainder. `_step-mul` consumes one `mul(`: the fragment up to the next `)` must split into two one-to-three-digit numbers (`_digits` walks the characters against `"0123456789"` since `text.to-int` would happily parse a minus sign); a valid instruction gains its product and skips past the paren, a malformed one rescans from just past `mul(` so an instruction nested inside a malformed one still surfaces, matching regex left-to-right semantics. Part 1 loops over `mul(` alone; part 2 finds the earliest of `mul(`, `do()`, and `don't()` each round (`_earliest` folds a `Token` record) and carries an enabled flag — `do()`/`don't()` being independent literals, neither matches inside the other.

**Sample answers.** Part 1 `161`, part 2 `161` (`samples/day03.txt`, the public worked example; part 1's value matches the page). The sample memory holds no do()/don't() instructions, so both parts see the same enabled run; the test file adds a crafted toggle line (`mul(2,4)don't()mul(5,5)do()mul(3,3)`, expecting 17) so the disabling path is still checked.

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day03.py` (`enabled = True` at the start, `do()` sets it, `don't()` clears it, only enabled muls add) and timvisee/advent-of-code-2024 `day03b/src/main.rs` (one regex over mul/do/don't tokens, the same enabled filter). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 161.

**Runtime feel.** Instant on the sample; each round drops the remainder past the matched token.

**Gaps.** One expected friction, already known: no regex, so the scan is hand-rolled `index-of` stepping — same family as the epic's no-char-type trap, no new ticket. The day stays in the browser subset and keeps the run panel.

## Day 4 — Ceres Search

**Approach.** The grid stays a list of row strings, like 2025 day 4. `_cell` bounds-checks and returns a one-character slice (or `""` outside), which covers backwards spellings for free: part 1 starts at each `X` and walks all eight offsets (an `Offset` record list) three steps comparing against `MAS`; the reversed directions are just negative offsets. Part 2 centers on each `A` away from the border and accepts the cross when both diagonals hold `M` and `S` on opposite ends (`_is-mas-pair`, either order).

**Sample answers.** Part 1 `18`, part 2 `9` (`samples/day04.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day04.py` (an `A` center with both diagonal corner pairs equal to the set {M, S}) and timvisee/advent-of-code-2024 `day04b/src/main.rs` (the same center test, accepting the four corner layouts MMSS, MSMS, SSMM, SMSM). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 18.

**Runtime feel.** Instant on the sample (a 10x10 grid, eight offsets per X).

**Gaps.** None new — the known no-char-type friction (one-character slices through `text.slice`) is already on the epic's trap list. The day stays in the browser subset and keeps the run panel.

## Day 5 — Print Queue

**Approach.** `parse` splits on the line shape — a `|` makes an ordering rule, otherwise a comma list makes an update — into one `Manual` record of `Rule` records and updates. `_valid` checks every earlier/later page pair against `_violates` (a rule demanding the later page first). Part 1 sums the middle pages of valid updates (`list.length(update) / 2`, odd lengths by design). Part 2 sorts each invalid update with a hand-rolled stable insertion sort — `list.sort` ranks plain Int/String lists only, no comparator — where a page moves left past only pages the rules force it before (`_insert` rebuilds the list at the insertion point); unrelated pages keep their order, then the corrected middle pages are summed.

**Sample answers.** Part 1 `143`, part 2 `123` (`samples/day05.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day05.py` (invalid updates only, ordered by each page's applicable-rule count, middle summed) and timvisee/advent-of-code-2024 `day05b/src/main.rs` (a comparator sort on the pairwise rule, middle of each fixed update). Both fix only invalid updates and read the middle after fixing. The part-2 sample value came from a Go implementation (insertion sort by the pairwise rule); the same run reproduced part 1's published 143.

**Runtime feel.** Instant on the sample (21 rules, six updates of at most five pages).

**Gaps.** One design gap, ticketed as #164: `list.sort` accepts no comparator (S6's key-based forms rank by Int/String keys only) and there is no positional `list.insert`, so the rules-driven order is a hand-rolled stable insertion sort with a rebuild-to-insert helper — the batch brief itself anticipated this. One engine gap, already ticketed: the blank section separator forces the `error.detail` end-of-file branch, so the browser build fences with the `error.detail` note and the door carries no run panel, exactly like 2025 day 5 (#135, #155) — the Go interpreter reads the day fine.
## Day 6 — Guard Gallivant

**Approach.** The grid stays a list of row strings. One `_walk` word runs the whole patrol with an optional extra obstruction: every visited cell lands in a `Map<String, Bool>` keyed `"r:c"` (the set idiom — there is no set type) and every entered position-direction state in another keyed `"r:c:d"`; a repeated state ends the walk flagged as a loop, and a step off the map ends it clean. The direction is an index 0–3 with `_dr`/`_dc` deltas; turning right is `(direction + 1) % 4`. Part 1 is the visited map's length. Part 2 brute-forces the candidates: an obstruction can only change a walk that reaches it, so the original walk's cells (minus the start, which the puzzle excludes) are the only ones tried, each through `_walk` again with the loop flag read off the record. `Walk` is a small record (`cells`, `looping`) because a dot reads fields only after a bound name.

**Sample answers.** Part 1 `41`, part 2 `6` (`samples/day06.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: grantdotdev's walkthrough (dev.to, "AoC 24 Day 6: Guard Gallivant" — try an obstruction on each cell the guard's original path visits, and call it a loop when the same position-with-direction repeats, a `HashSet` of position plus direction in his C#) and unnecessary.tech's write-up ("AoC 2024 Day 6" — the test data holds 6 valid obstruction spots; his first attempt found only 3 by placing obstructions on already-traversed cells instead of new positions ahead of the guard). Both agree on rule and count; the Zhex run above reproduced both published sample answers.

**Runtime feel.** ~60 ms on the sample (10x10). Part 2 is candidates-times-walk-length — quadratic-ish on a real 130x130 input and likely slow there in an interpreter; samples are the gate, so nothing was optimized.

**Gaps.** None new — the Map-as-set idiom is the epic's known shape (a `Set` type sits in the standard-library plan's Collections future), and `map.put`'s pass-through return wants a `let updated = ...` binding when it ends an `if` branch, the documented maps idiom. Runner shape unchanged from the 2023 lane (sentinel `catch` end-of-file, `dayNN`/`dayNN-core` split); browser compile succeeds, no WasmNote.

## Day 7 — Bridge Repair

**Approach.** `parse` reduces each line to an `Equation` record (test value, operand list) — split at the colon, then spaces, `text.to-int` per token with the fallible-parse idiom. Both parts share `_solvable`, a recursive search inserting one operator per level with the current value riding the recursion: `+`, `*`, and in part 2 `||`. Concatenation is pure string work — `int.to-string(a) + b` joins the digits through the string-context Int exception, then `text.to-int` parses it back (`catch 0`; operands are nonnegative so the parse cannot fail). No pruning: `* 0` can shrink the current value, so a current-above-test cut would be wrong, and the operand count (the recursion depth) is tiny anyway.

**Sample answers.** Part 1 `3749`, part 2 `11387` (`samples/day07.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2024 `Day07.scala` + `Day07Test.scala` (part 2 adds `'|'` implemented as string concatenation `s"$partialResult${parts.head}"`, and the test asserts 3749 and 11387 on the example input) and javorszky's walkthrough (javorszky.co.uk, day 7 — a third concatenate operator, enumerated by counting in base 3 over the gaps). Both agree on the rule; the Zhex run above reproduced both sample answers.

**Runtime feel.** ~45 ms on the sample. The search is 2^(gaps) or 3^(gaps) per equation — single-digit gaps here; a real input's ~12 operands stays 3^11 worst case per line, noticeable but bounded in an interpreter.

**Gaps.** None new — the string-context Int exception did the digit-joining without any new word shape. Runner and browser compile unchanged from day 6; no WasmNote.

## Day 8 — Resonant Collinearity

**Approach.** `_antennas` collects every non-dot cell as an `Antenna` record (frequency, row, column), and antinodes collect in a `Map<String, Bool>` keyed `"r:c"` — the set idiom again. Part 1 walks every same-frequency pair (nested index loops) and marks the two mirror points `2a - b` and `2b - a` when in bounds. Part 2 marks the pair's whole line: the step is the pair's delta divided by its gcd (`_gcd` walks Euclid), so the walk lands on every lattice point of the line — including points *between* the two antennas, which the raw delta would skip when it is not primitive — and it starts at one antenna and runs both directions until off the map, so the antennas themselves count. The sample's pairs all happen to have primitive deltas, but the rule text says any point perfectly in line, so the primitive step is the correct reading.

**Sample answers.** Part 1 `14`, part 2 `34` (`samples/day08.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2024 `Day08.scala` + `Day08Test.scala` (part 2 iterates the pair's delta outward from both antennas — distance 0 puts the antennas in the antinode set — and the test asserts 14 and 34 on the example input) and javorszky's walkthrough (javorszky.co.uk, day 8 — generate antinodes repeatedly along the same line until off the map, both antenna coordinates in the starting vector). Both agree on the rule; the Zhex run above reproduced both sample answers.

**Runtime feel.** ~50 ms on the sample (12x12). Pairs-per-frequency is small; a real input's ~50 antennas per frequency makes the pair loops quadratic but still interpreter-comfortable.

**Gaps.** None new — same Map-as-set known shape as day 6. Runner and browser compile unchanged; no WasmNote.

## Day 9 — Disk Fragmenter

**Approach.** `parse` expands the dense line into one block list — file IDs for files, `-1` for free — the first nonempty line only. Both parts work on a copy (`list.append` loop), leaving the parsed disk reusable. Part 1 is two pointers: the last file block fills the leftmost free block until the pointers meet, a `while` with indexed reads and writes (never inside a list traversal — the `for index in range` discipline of the 2023 lane). Part 2 moves whole files, highest ID down: `_file-span` locates one file's start and length, `_first-hole` scans left to right for the first run of free blocks at least that long and entirely left of the file (one pass with a run-start cursor, -1 when nothing fits), and the move rewrites the hole then blanks the old span — the hole's leftover stays free naturally. The shared `_checksum` sums position times file ID over file blocks.

**Sample answers.** Part 1 `1928`, part 2 `2858` (`samples/day09.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2024 `Day09.scala` + `Day09Test.scala` (part 2 iterates files reversed by ID into the first space segment at least as long and positioned before the file, never splitting, and the test asserts 1928 and 2858 on `2333133121414131402`) and javorszky's walkthrough (javorszky.co.uk, day 9 — whole files from the highest ID backwards, first gap at least as long before the file's start, the vacated span becomes free space). Both agree on the rule; the Zhex run above reproduced both sample answers.

**Runtime feel.** ~45 ms on the sample (42 blocks). A real input's ~20k blocks makes part 2 one linear hole scan per file — seconds at worst, linear in files; nothing was optimized past that.

**Gaps.** None new. The day leaned on exactly the lane's established shapes: indexed writes inside `while` loops, records for the file span, `_`-private helpers. Runner and browser compile unchanged; no WasmNote.

## Day 10 — Hoof It

**Approach.** `_height` reads one digit cell through `text.to-int` with a `catch -1`. Part 1 scores each 0-cell with a breadth-first walk: the queue is a `List<Int>` of positions encoded `row * width + column` and index-walked (the List-as-queue idiom), the visited set is the `Map<String, Bool>` `"r:c"` key idiom, and `_climb` queues the in-bounds neighbors at height + 1; a 9-cell found unvisited adds one to the score. Part 2 rates each trailhead with `_paths`, a recursive count over the four uphill neighbors — every distinct trail adds 1, and the strictly climbing trail caps the call depth at ten, far inside the 256 limit. No memoization: the sample's eight-by-eight map needs none.

**Sample answers.** Part 1 `36`, part 2 `81` (`samples/day10.txt`, the larger public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2024 `Day10.scala` + `Day10Test.scala` (part 2 enqueues whole trails instead of visited positions, counting every distinct path, and the test asserts 36 and 81 on the larger example) and javorszky's walkthrough (javorszky.co.uk, day 10 — the rating counts all the separate ways to reach the summits; the page's example answer is 81). Both agree on the rule; the Zhex run above reproduced both sample answers.

**Runtime feel.** ~55 ms on the sample (8x8). The per-trailhead walks are grid-sized; a real 140x140 input stays linear-ish and comfortable.

**Gaps.** None new — the same known shapes (Map-as-set, encoded queue positions, recursive count). Runner and browser compile unchanged; no WasmNote.


## Day 21 — Keypad Conundrum

**Approach.** No sequence is ever materialized. A per-pair cost table `Map<String, Int>` keyed by the two button characters holds, for one level of the directional-keypad chain, the cheapest number of presses to move between two buttons and press. Level one is just Manhattan distance plus one; each further level is `_best-table`: for every button pair, enumerate the minimal gap-avoiding move strings (`_walk` interleaves the vertical and horizontal moves recursively, dropping any ordering whose next cell is the gap — each distinct interleaving appears exactly once) and keep the cheapest one typed through the previous level (`_typing-cost` sums the table over consecutive characters starting from `A`). The numeric keypad then runs its own pairs through the final table, and a code's complexity is its typing cost times its numeric part. Positions are encoded `row * 10 + column`, gaps at 0 (directional) and 30 (numeric). Part 2 is the same word with the chain length 25 instead of 2 — the chain count is the robots between the top keypad and the first one typing on the numeric pad, so the puzzle's "you plus two robots" is a table of level two; the Go cross-check oracle settled that off-by-one before any Zhex was written.

**Sample answers.** Part 1 `126384`, part 2 `154115708116294` (`samples/day21.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: sanraith/aoc2024 `Day21Test.scala` (part 2 uses 25 directional-pad robots, and the test asserts 126384 and 154115708116294 on the five-code example) and the Elixir Forum thread "Advent of Code 2024 Day 21" (liamcmitchell posts the part 2 example answer 154115708116294; ken-kost's code builds one numeric plus 25 directional pads). A Go oracle implementing the same level table reproduced both sample answers before the Zhex port.

**Runtime feel.** ~75 ms on the sample. The dominant cost is 25 levels of 25 pairs over paths of at most three moves — a few thousand map operations in total; a real input adds five longer codes and stays trivial.

**Gaps.** None new — Map literals as position tables and the `match map[key]` Option read are existing shapes. Runner and browser compile unchanged from day 10; no WasmNote.
