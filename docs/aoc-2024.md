# Advent of Code 2024 — findings log

Dogfooding log for solving Advent of Code 2024 in Zhex (archive epic #136): one section per day, recording the approach, the sample answers, the runtime on the sample input, and the interpreter gaps the day hit — each gap becomes a ticket number. The truth surfaces (`aocSpecs` in `tools/site-data`, ROADMAP) are updated by the stories; this log captures the reasoning in between.

## Day 1 — Historian Hysteria

**Approach.** `parse` splits each line on its single space into the two columns, held in one `Lists` record. Part 1 sorts both columns (`list.sort` returns sorted copies) and totals the rank-by-rank distances, negating the difference when the left value is smaller — there is no `abs` word. Part 2 counts the right column into a `Map<Int, Int>` (the `_seen` helper turns the `Option` read into a plain count), then totals each left ID times its count.

**Sample answers.** Part 1 `11`, part 2 `31` (`samples/day01.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day01.py` (`sum(x * _right.count(x) for x in _left)`) and timvisee/advent-of-code-2024 `day01b/src/main.rs` (a counting array indexed by the right IDs, each left ID multiplied by its entry). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 11. The Observable walkthrough (observablehq.com/d/a87155f309efaf26) independently states 31 for the same lists.

**Runtime feel.** Instant on the sample; nothing to measure.

**Gaps.** None new — the runner reuses the 2025 sentinel read loop (#134, #135) and the day compiles to the browser subset, so the door gets its run panel.

## Day 2 — Red-Nosed Reports

**Approach.** `parse` splits each line on spaces into one `List<Int>` per report. `_safe` walks the steps once, tracking whether any step breaks the increasing run, the decreasing run, or the 1..3 bound; a report passes when one direction survives and the bound holds — a zero step kills both directions, so equal neighbors stay unsafe. Part 1 counts the safe reports. Part 2 retries each report with one level removed (`_without` rebuilds the row), accepting the report when any removal is safe; the retry loop stops at the first tolerated removal.

**Sample answers.** Part 1 `2`, part 2 `4` (`samples/day02.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day02.py` (tries every single-level removal) and timvisee/advent-of-code-2024 `day02b/src/main.rs` (`(0..nums.len()).any(|i| ...)` over each removal with the same direction-and-bound fold). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 2.

**Runtime feel.** Instant on the sample (six five-level reports, at most five removals each).

**Gaps.** None new — the removal trial is plain loops; the day stays in the browser subset and keeps the run panel.

## Day 3 — Mull It Over

**Approach.** There is no regex, so both parts scan by `text.index-of` over a shrinking remainder. `_step-mul` consumes one `mul(`: the fragment up to the next `)` must split into two one-to-three-digit numbers (`_digits` walks the characters against `"0123456789"` since `text.to-int` would happily parse a minus sign); a valid instruction gains its product and skips past the paren, a malformed one rescans from just past `mul(` so an instruction nested inside a malformed one still surfaces, matching regex left-to-right semantics. Part 1 loops over `mul(` alone; part 2 finds the earliest of `mul(`, `do()`, and `don't()` each round (`_earliest` folds a `Token` record) and carries an enabled flag — `do()`/`don't()` being independent literals, neither matches inside the other.

**Sample answers.** Part 1 `161`, part 2 `161` (`samples/day03.txt`, the public worked example; part 1's value matches the page). The sample memory holds no do()/don't() instructions, so both parts see the same enabled run; the test file adds a crafted toggle line (`mul(2,4)don't()mul(5,5)do()mul(3,3)`, expecting 17) so the disabling path is still checked.

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day03.py` (`enabled = True` at the start, `do()` sets it, `don't()` clears it, only enabled muls add) and timvisee/advent-of-code-2024 `day03b/src/main.rs` (one regex over mul/do/don't tokens, the same enabled filter). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 161.

**Runtime feel.** Instant on the sample; each round drops the remainder past the matched token.

**Gaps.** One expected friction, already known: no regex, so the scan is hand-rolled `index-of` stepping — same family as the epic's no-char-type trap, no new ticket. The day stays in the browser subset and keeps the run panel.

## Day 4 — Ceres Search

**Approach.** The grid stays a list of row strings, like 2025 day 4. `_cell` bounds-checks and returns a one-character slice (or `""` outside), which covers backwards spellings for free: part 1 starts at each `X` and walks all eight offsets (an `Offset` record list) three steps comparing against `MAS`; the reversed directions are just negative offsets. Part 2 centers on each `A` away from the border and accepts the cross when both diagonals hold `M` and `S` on opposite ends (`_is-mas-pair`, either order).

**Sample answers.** Part 1 `18`, part 2 `9` (`samples/day04.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day04.py` (an `A` center with both diagonal corner pairs equal to the set {M, S}) and timvisee/advent-of-code-2024 `day04b/src/main.rs` (the same center test, accepting the four corner layouts MMSS, MSMS, SSMM, SMSM). The part-2 sample value came from a Go implementation of that agreed rule; the same run reproduced part 1's published 18.

**Runtime feel.** Instant on the sample (a 10x10 grid, eight offsets per X).

**Gaps.** None new — the known no-char-type friction (one-character slices through `text.slice`) is already on the epic's trap list. The day stays in the browser subset and keeps the run panel.

## Day 5 — Print Queue

**Approach.** `parse` splits on the line shape — a `|` makes an ordering rule, otherwise a comma list makes an update — into one `Manual` record of `Rule` records and updates. `_valid` checks every earlier/later page pair against `_violates` (a rule demanding the later page first). Part 1 sums the middle pages of valid updates (`list.length(update) / 2`, odd lengths by design). Part 2 sorts each invalid update with a hand-rolled stable insertion sort — `list.sort` ranks plain Int/String lists only, no comparator — where a page moves left past only pages the rules force it before (`_insert` rebuilds the list at the insertion point); unrelated pages keep their order, then the corrected middle pages are summed.

**Sample answers.** Part 1 `143`, part 2 `123` (`samples/day05.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day05.py` (invalid updates only, ordered by each page's applicable-rule count, middle summed) and timvisee/advent-of-code-2024 `day05b/src/main.rs` (a comparator sort on the pairwise rule, middle of each fixed update). Both fix only invalid updates and read the middle after fixing. The part-2 sample value came from a Go implementation (insertion sort by the pairwise rule); the same run reproduced part 1's published 143.

**Runtime feel.** Instant on the sample (21 rules, six updates of at most five pages).

**Gaps.** One design gap, ticketed as #164: `list.sort` accepts no comparator (S6's key-based forms rank by Int/String keys only) and there is no positional `list.insert`, so the rules-driven order is a hand-rolled stable insertion sort with a rebuild-to-insert helper — the batch brief itself anticipated this. One engine gap, already ticketed: the blank section separator forces the `error.detail` end-of-file branch, so the browser build fences with the `error.detail` note and the door carries no run panel, exactly like 2025 day 5 (#135, #155) — the Go interpreter reads the day fine.

## Day 11 — Plutonian Pebbles

**Approach.** `parse` splits the stone line on spaces into `List<Int>`. The line grows past listing, so both parts count stone values into a `Map<Int, Int>` and map counts to counts each blink (`_blink`): the 0 rule writes straight through, the split is arithmetic — digit count from `int.to-string`'s length, halves by dividing and taking the remainder of a power of ten, so `text.to-int` never runs outside `parse` — and the grow rule multiplies by 2024. `_after` runs the round the asked number of times and totals the counts; the parts differ only in 25 versus 75 blinks. Distinct stone values stay in the thousands, so 75 rounds are instant.

**Sample answers.** Part 1 `55312`, part 2 `65601038650482` (`samples/day11.txt`, the public worked example; part 1's value matches the page, and the page's six intermediate blink lines pin the rule reading).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day11.py` (`blink(stone, 75)` under a memo table, same three rules) and mebeim/aoc `2024/original_solutions/day11.py` (`calc(i, limit=75)` with `lru_cache`). The part-2 sample value came from a Go implementation of the agreed rules; the same run reproduced the page's 55312 and every intermediate blink line.

**Runtime feel.** Instant on the sample (75 rounds over a map of a few thousand values).

**Gaps.** None new — map counting is the day-1 idiom, and the arithmetic split avoids a second `to-int` family. The runner reuses the sentinel read loop, so the day stays in the browser subset and keeps the run panel.

## Day 12 — Garden Groups

**Approach.** The grid stays a list of row strings and cells are encoded as `row * width + column`. Regions grow through `_region`, a worklist with a cursor — lists have no pop, so the cursor walks a growing list — collecting into a shared `seen` list through `_has`. `_same` (in bounds and same letter) doubles as the in-region test, since regions are maximal. Part 1 sums area times perimeter, each plot contributing its sides without a same-letter neighbor (`_edges`). Part 2 sums area times sides: a region's straight sides equal its corners, outward where two orthogonal neighbors leave the region and inward where both stay and the diagonal leaves (`_corners`), so eight looks per plot replace the perimeter walk.

**Sample answers.** Part 1 `140`, part 2 `80` (`samples/day12.txt`, the first public worked example; part 1's value matches the page). The test file also checks the page's other two maps — 772/436 and 1930/1206 — locking both parts beyond the first example.

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day12.py` (`get_group_sides` scans row pairs for fence-run starts in all four directions) and mebeim/aoc `2024/original_solutions/day12.py` (`sides` unions contiguous same-direction fence edges into maximal runs). Both count straight runs, which equals the corner count for any orthogonal region. The Go oracle implemented both algorithms; they agreed on all three maps (80, 436, 1206) and reproduced the page's 140, 772, and 1930.

**Runtime feel.** Instant on the sample (the ten-by-ten map's `_has` membership is quadratic but tiny).

**Gaps.** None new — the no-pop worklist is the cursor idiom again, and the hand-rolled `_has` membership is the already-ticketed `list.contains` gap (#163). The day stays in the browser subset and keeps the run panel.

## Day 13 — Claw Contraption

**Approach.** `parse` splits machine blocks on the blank line, then each line on `": "` and `", "`; every value fragment drops its two-character `X+`, `Y+`, `X=`, or `Y=` prefix before `text.to-int`. Both parts solve each machine exactly with integer algebra — determinant `ax*by - ay*bx`, Cramer numerators for both press counts, exact-remainder divisibility check, non-negativity check — no floats anywhere. Part 1 keeps solutions with at most 100 presses per button (`_won-cost`'s cap); part 2 builds each machine's far copy with both prize coordinates plus 10000000000000 and drops the cap through a negative-cap convention, noted in the word.

**Sample answers.** Part 1 `480`, part 2 `875318608908` (`samples/day13.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day13.py` (part 2 adds 10000000000000 to both prize coordinates, keeps the integer check, drops the 100 cap) and mebeim/aoc `2024/original_solutions/day13.py` (`smartcalc` solves the offset system with z3 integer variables, same 3a+b cost). The part-2 sample value came from a Go implementation of the agreed rule; the same run reproduced part 1's published 480.

**Runtime feel.** Instant on the sample (four machines, six integers each).

**Gaps.** One engine gap, already ticketed: the blank line between machines forces the `error.detail` end-of-file branch, so the browser build fences the day and the door carries no run panel, like day 5 (#135, #155). No new language friction — the integer algebra is plain arithmetic.

## Day 14 — Restroom Redoubt

**Approach.** `parse` splits each `p=x,y v=x,y` line on the space, then each half on `=` and `,`. `_mod` wraps positions for negative drifts (Zhex `%` truncates toward zero, so add-then-remainder twice). The space size follows the input: twelve robots mean the page's 11x7 example, anything else the full 101x103 restroom — the puzzle states both sizes and the community convention is the count test. Part 1 wraps each robot 100 seconds forward, drops the middle row and column, and multiplies the four quadrant counts. Part 2 hunts the Easter-egg frame as the first second at which no two robots share a tile (`_distinct` sorts encoded tile ids and checks neighbors) — the tree frame is the one clumped drawing and its robots never overlap; honestly, on the twelve-robot sample that first no-overlap second is 1, so the sample value checks the rule, not the picture.

**Sample answers.** Part 1 `12`, part 2 `1` (`samples/day14.txt`, the public worked example; part 1's value matches the page).

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day14.py` (part 2 returns the first `t` where all robot tiles are distinct) and mebeim/aoc `2024/original_solutions/day14.py` (scans frames for the maximum adjacent-robot count, with the note that no robot shares a tile in the tree frame). Both aim at the same picture frame; the Zhex solution follows the no-overlap reading. The part-2 sample value came from a Go implementation of both heuristics (no-overlap gives 1 on the sample, adjacency peaks at second 6, neither meaningful at twelve robots); the same run reproduced part 1's published 12.

**Runtime feel.** Instant on the sample (the scan stops at second 1). A full-size input walks thousands of frames, one sort of five hundred ids each — minutes at worst, not hours, and no frame limit is needed because the pattern repeats.

**Gaps.** None new — the sorted-adjacent duplicate check replaces the hand-rolled membership loop. The day stays in the browser subset and keeps the run panel.

## Day 15 — Warehouse Woes

**Approach.** The warehouse is a rank-2 `Array<String>` of one-character tiles, the Game of Life shape, plus the move list (`parse` splits the map from the moves on the blank line). Part 1 pushes single-tile boxes: one chain scan along the move direction finds the first gap, and a copy-back loop shifts the whole run into it (`_step-one`), wall-blocked moves leave everything in place. Part 2 scales the map to double width (`_scaled`: `#` to `##`, `O` to `[ ]`, `@` to `@.`) and pushes boxes as pairs — horizontal pushes shift the run of halves the same way, vertical pushes collect every half that must move by walking the pairs ahead of the robot through `_lifted` (worklist with a cursor), then shift them farthest row first (`_shift`), so stacked or straddling boxes cascade correctly. Each part works on its own grid copy, keeping `parse`'s map pristine for the other part. GPS counts `O` tiles in part 1 and `[` halves in part 2.

**Sample answers.** Part 1 `10092`, part 2 `9021` (`samples/day15.txt`, the page's larger worked example; both values match the page). The test file also checks the small eight-by-eight map — 2028 and 1751, the latter from the oracle — so both push shapes are covered twice.

**Part 2 sources.** Two agreed: nitekat1124/advent-of-code-2024 `solutions/day15.py` (part 2 scales the grid, BFS-collects the box halves ahead of a vertical push, sums GPS over `[`) and mebeim/aoc `2024/original_solutions/day15.py` (tracks box halves as pairs in a dict, same scaled GPS summed over both halves then halved). The page publishes 9021 for the scaled larger example; the Go oracle reproduced 10092 and 9021 exactly, plus 2028 and 1751 on the small map, and a line-by-line frame diff against the Zhex run fixed one real bug mid-arc (`_shift` dropped the row directly in front of the robot).

**Runtime feel.** About sixty milliseconds on the sample (ten-by-ten map, eight hundred moves); a full-size input stays in the same shape of seconds.

**Gaps.** One engine gap, already ticketed: the blank line between map and moves forces the `error.detail` end-of-file branch, so the browser build fences the day and the door carries no run panel, like day 5 (#135, #155). The `_has` membership in `_lifted` is the `list.contains` gap again (#163); chains are short, so the quadratic check is harmless here.
