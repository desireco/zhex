# Initial Zhex language contract

This contract defines the first Go interpreter and the executable examples used to validate it. Zhex is a Forth-inspired language with named values and checked composition. The initial implementation executes a checked syntax tree; it does not generate native code.

## Source and blocks

Source is valid UTF-8. Blocks use four spaces per indentation level; tabs outside strings and comments are rejected. Blank lines and `#` comments are ignored. Statements end at a newline; parentheses do not introduce multiline continuation in this version. Syntax nesting and expression-tree depth are limited to 256 to report overly deep source as a language error.

Names use ASCII letters, digits, and underscores, starting with a letter or underscore. Hyphen-separated name segments beginning with a letter or underscore are allowed, as in `is-palindrome`. Dots qualify operation names: a dot names the type or module that owns the word. A dot after a record value reads a field, as in `customer.name`; field paths may be nested. A leading underscore marks a word or type module-private (see Modules). Consequently `a-b` is a name, while `a - b` is subtraction: use spaces around subtraction between names. Keywords cannot be binding or word names; `use` is one of them. Strings use double quotes and Go-style escapes, and must decode to valid UTF-8.

## Values and expressions

The built-in value types are `Int`, `Bool`, `String`, and `Unit`, plus the `Buffer` and `File` resource types described with the standard operations. Named record types contain typed fields. `List<T>` and `Array<T>` are homogeneous mutable collection types. Selected operations also return a `Result<T, E>` value. A word can declare that as its result type; the supported error families are `InputError`, `ParseError`, `FileError`, `BufferError`, and the common `Error` type. Result values must be handled or propagated immediately. `Int` is a signed 64-bit integer. Literals include decimal integers, `true`, `false`, strings, and homogeneous list literals such as `[1, 2, 3]`. Negative integer literals include the full signed range. Overflow is a language error; division and remainder by zero are errors. Division truncates toward zero; remainder has the dividend's sign. The minimum integer divided by `-1` overflows; its remainder modulo `-1` is zero.

Precedence, from lowest to highest: `or`, `and`, `== !=`, `< <= > >=`, `+ -`, `* / %`, unary `-`/`not`, calls, record-field and collection-index access, and postfix `try`. Binary operators associate left. Operands, call arguments, index expressions, and assigned values evaluate left to right; `and` and `or` short-circuit. Arithmetic requires integers, except `+` also concatenates two strings. Ordering requires integers. Equality compares matching `Int`, `Bool`, or `String` values. There are no implicit conversions.

`let name = expression` creates an immutable binding. `var name = expression` allows assignment with `name = expression`, preserving its inferred type. Either binding can include an explicit type annotation: `let name: Type = expression` or `var name: Type = expression`. The checker requires the expression's type to match the annotation. Bindings have lexical block scope; duplicates in one scope are errors. Inner scopes can shadow outer names. Parameters are immutable.

## Records and named types

`type Customer = record` declares a nominal record type followed by indented `field: Type` declarations. A record value is constructed positionally in declaration order, as `Customer("Ada", 36)`, and its immutable fields are read with `customer.name`. Fields can contain shared mutable collections. A record declaration is the initial named-type form, not a type alias; other user-defined types remain future work. See [records and named types](../site/src/content/docs/records.md).

## Lists and arrays

`List<T>` is a homogeneous growable list; `Array<T>` is a homogeneous rectangular array with runtime shape. Nonempty list literals infer a common element type; empty list literals and `list.new()` require an expected `List<T>` type. Array dimensions are a `List<Int>` and are supplied to `array.new(dimensions, fill)`. Nested list literals do not implicitly convert to arrays. Both collection types share mutable storage across assignments and parameters. `let` fixes a binding name, not the referenced collection.

`list.length` returns an `Int`; `list.append` returns `Result<Unit, Error>`. Collection elements use zero-based checked brackets: `values[i]` reads one list element and `grid[i, j]` reads an array cell. Assign with `(values[i] = value)` or `(grid[i, j] = value)`. Reads and writes return Results and fail on an invalid index. `array.rank`, `array.length`, and `array.shape` inspect dimensions; `array.resize` changes dimensions without changing rank and preserves values at overlapping coordinates. Array rank is 2 through 32, extents are nonnegative, and list/array size is limited to 1,000,000 elements. See [lists and arrays](../site/src/content/docs/collections.md) for exact operations, error codes, and mutation behavior.

## Words and composition

`word name(parameter: Type, ...) -> Type` introduces a top-level definition followed by an indented body. Parameter and result types are explicit. A word's declared result may be `Result<T, E>`; parameters still use the ordinary value types. Definitions may call other definitions, including forward references. The final statement supplies the word result; bindings, assignments, loops, and empty blocks have type `Unit`. Words do not capture top-level local bindings. Recursive calls have a runtime depth limit of 256.

Call a word with `name(arguments)`. A `flow expression` block contains one word name per line; each word receives the previous value as its single argument. Mark a fallible flow step with postfix `try`, for example `parse-count try`; a bare fallible flow step is rejected. The final step's value is the flow's result. Calls are resolved and their input/output types checked before execution. Named calls and flow steps use the same operations.

## Results, propagation, and recovery

The built-in error families are `InputError`, `ParseError`, `FileError`, and `BufferError`; `Error` is a common family for application-created or explicitly converted errors. Word signatures can declare one of these families, such as `Result<Int, ParseError>`. There are no user-defined error types.

Inside a fallible word, postfix `try` unwraps a successful Result. A failure propagates to the caller as the word's declared Result, provided its error family matches exactly. At the program boundary, top-level `try` preserves the existing behavior: the unhandled error is reported as a source-located diagnostic and the run exits nonzero. A non-fallible word cannot propagate a Result failure with `try`.

`ok(value)` constructs the success case in a fallible word. `err(error)` constructs the failure case; the error family must match the word's declared Result. `error.new(code, message)` creates a cause-less common `Error` at that call site. `error.wrap(code, message, cause)` creates a common `Error` that retains the cause and its original origin. Error families do not widen implicitly: a caught concrete error may be passed directly to built-in `error.*` operations, but must be wrapped before passing to a user-defined word that accepts `Error` or storing/returning it in an `Error` field or collection. Pass a wrapped error directly in a named call; a flow cannot pass an Error value to a user-defined step, even when wrapped.

`catch` follows a Result-producing expression as a statement and may bind the error: `let value = operation() catch problem` followed by an indented handler. The handler runs only on failure and its final statement must have the Result's success type. It may use `return err(...)` to exit early from a fallible word. `catch` does not intercept runtime faults such as overflow or division by zero.

A Result-producing expression cannot be discarded. A bare fallible call is rejected. A Result stored by `let` must be handled immediately: the next statement in the same block must be exactly `pending try` or `pending catch ...`, either as a standalone expression or as the full right-hand side of a new `let`. It cannot be put in `var`, aliased, passed to another word, or handled later or conditionally. The REPL applies the same rule to each entry.

Errors can be inspected with `error.code`, `error.message`, `error.operation`, `error.file`, `error.line`, `error.column`, and `error.detail`. `error.has-cause` checks for a cause; `error.cause` returns a Result that fails with `error-no-cause` when absent. Error bindings are immutable. See [diagnostics and tracing](../site/src/content/docs/diagnostics.md) for the exact signatures.

An application may set a named reporter using `error.set-reporter(report-word)` at top level before fallible calls; the word must have signature `(Error) -> Unit`. `error.report(problem)` explicitly reports a failure that the application handled. A failure escaping the program invokes the reporter automatically once before the regular diagnostic. Intermediate propagation does not notify the reporter. Reporter failures do not replace the original result or runtime error, and `console.exit` or `console.fail` inside the reporter cannot override the original outcome. There is no external reporting destination by default. Codes supplied to `error.new` and `error.wrap` are application-owned and are not entries in the built-in diagnostic catalog.

`console.exit(status)` terminates execution with a deliberate status from `0` through `255` and can be used as a `catch` fallback instead of producing a value. A valid exit is not a diagnostic and does not call the automatic reporter. An out-of-range status raises the source-located `console-exit-status` runtime diagnostic, which can be reported. `console.fail(message)` writes the message and a newline to standard error, then terminates with status `1`; it is also a valid `catch` fallback and does not call the automatic reporter. These exits close active `file.lines` streams; files opened explicitly with `file.open` remain the program's responsibility to close with `file.close`. If either operation runs inside a reporter, it cannot replace the original outcome. In the REPL, `console.exit` and `console.fail` end the entire process.

## Modules

A program splits across files. `use math` at the top level of a file imports the module named `math` by loading the sibling `math.zhex` next to the importing file — each file's own imports resolve beside it. A module that cannot be loaded is a `use-missing` error naming the searched path. `use` is a keyword and is allowed only at a file's top level (`use-location`); a repeated `use` of the same module is a no-op.

An imported word is called qualified, as in `math.gcd(a, b)` or a flow step. Inside its own file a module's words call each other bare, and they cannot see the importing file's words. A word or record type whose name starts with an underscore is private to its module: usable only inside its own file, never suggested outside it, and reached from another file only as a `private-use` error. Public word signatures and record fields cannot expose a private type, including through `List`, `Array`, or `Result`. A module's own imports stay private to it — naming a module directly is the only way to see its words and types — and two modules never collide, even when their names share names. Duplicate word and type names are detected per file, and an entry file cannot redefine an adopted qualified name.

Module names `text`, `int`, `buffer`, `file`, `console`, `error`, `list`, and `array` are reserved (`use-reserved`); those prefixes belong to the standard operations. An imported file may declare words and types — top-level statements are a `module-body` error — and import cycles are `use-cycle` errors spelling the files in the cycle. Every loaded module checks before the file that imports it, so dependencies report first, and module errors annotate the module's own source at check time and at runtime.

The REPL resolves `use` against the working directory and adopts each named module for the rest of the session; its qualified words then persist across entries and list under `words`. The two-file [modules example](../examples/modules/main.zhex) shows the shape: `main.zhex` runs the program and `math.zhex` beside it supplies the words, one of them underscore-private.

## Decisions and iteration

`if condition`, optional `elif condition` blocks, and optional `else` select a branch. Conditions must be `Bool`. Branch result types must match; a missing `else` supplies `Unit`. Each branch has its own lexical scope.

`for name in range(start, end)` iterates upward over integers with an exclusive end, without building a list. Bounds evaluate once. If `start >= end`, the loop is empty. The iteration binding is immutable and each iteration has its own block scope. The loop result is `Unit`.

`for line in file.lines(path)` iterates over the lines of a UTF-8 text file without holding the whole file. The path is a `String` evaluated once; each line is chomped like `read-line` (one trailing LF and an immediately preceding CR removed) and bound as an immutable `String` with its own block scope. An empty file runs no iterations; a final line without its newline still runs. The file is closed when the loop finishes and on every exit, including a failure in the loop body. A path that cannot be opened is a `file-open` error; content that is not valid UTF-8 is a `file-utf8` error. `range` and `file.lines` exist only in these loop syntaxes.

`for value in collection` traverses a list or array. Optional dual bindings are `for index, value in list` and `for coordinates, value in array`; indices are zero-based `Int`s, while array coordinates are a fresh `List<Int>` for each cell. The collection expression is evaluated once. Lists visit increasing indices and arrays visit in row-major order, with the last coordinate changing fastest. Empty collections run no iterations. A collection cannot be mutated while it is actively traversed, even through an alias; checked mutation returns `collection-iterating` before changing it. The guard is released on normal completion and all exits. See [collection iteration](../site/src/content/docs/iteration.md).

## Standard operations and console input

The initial predeclared operations are `print`, `int.to-string`, `text.reverse`, `read-line`, and `text.to-int`. `print` accepts one `Int`, `Bool`, or `String`, writes it followed by a newline, and returns `Unit`. Boolean text is `true` or `false`. `int.to-string` takes an integer. `text.reverse` takes a string and reverses Unicode code points without normalization. A dot qualifies an operation with its owner type or module; a dot after a record value selects a field. The original core operations include bare names such as `print` and `read-line`.

The `text` words operate on `String` values, Unicode-safe by code point. `text.length` counts code points. `text.line-count` counts lines — empty text is `0`, and a trailing newline does not add a line. `text.word-count` splits on Unicode whitespace. `text.upper` and `text.lower` map case; `text.trim` removes surrounding Unicode whitespace. `text.contains(text, part)` reports whether `part` occurs. `text.index-of(text, part)` returns the code-point position of the first occurrence, or `-1` when absent. `text.slice(text, start, end)` returns the code points from `start` up to `end`; bounds below zero and past the length clamp, and `start >= end` yields the empty string. `text.replace(text, old, new)` rewrites every occurrence of `old` with `new` — literally, not as a pattern; empty `old` is a `replace-empty` error, a bug signal rather than a recoverable case.

`Buffer` is a growable list of `String` lines for building text incrementally. `buffer.new()` creates an empty buffer; `buffer.add-line(b, line)` appends a line and returns `Unit`; `buffer.line-count(b)` returns the number of lines; `buffer.line(b, i)` returns `Result<String, BufferError>`, failing `buffer-range` on an index outside the lines; `buffer.set-line(b, i, line)` returns `Result<Unit, BufferError>` under the same rule; `buffer.to-text(b)` joins the lines with newlines. `let` binds the name, not a copy, so a second name observes the same buffer. Buffers are excluded from `==` and `!=`, and `print` rejects a `Buffer` with a hint to convert through `buffer.to-text`.

Files read through two layers. The whole-file layer returns everything at once: `file.read-all(path)` yields `Result<String, FileError>`, and `file.read-lines(path)` yields `Result<Buffer, FileError>` with every line chomped. The streaming layer holds an open handle: `file.open(path)` yields `Result<File, FileError>`; `file.read-line(f)` yields the next chomped line as `Result<String, FileError>`, and reaching the end of file fails inside the `Result`; `file.close(f)` releases the handle, returns `Unit`, and is safe to call twice, while reading from a closed file fails. The `for line in file.lines(path)` loop covers the streaming case with the close guaranteed on every exit. Files are read as UTF-8 and validated at the boundary; a path that cannot be opened fails `file-open`, naming the path and the operating system's reason. A `File` is excluded from `==` and `!=`, and `print` rejects it.

`read-line(prompt)` takes a string prompt and returns `Result<String, InputError>` from one line of standard input. `text.to-int(text)` is the inverse of `int.to-string`: it parses a signed 64-bit decimal, trimming surrounding whitespace, and returns `Result<Int, ParseError>`. Program arguments arrive the same way: `zhex run <file> [args...]` forwards non-option arguments after the source file to the program; `--trace` and `--report=text|json` remain interpreter options wherever they occur, and other `--` options are rejected, `console.args-count()` returns how many there are, and `console.arg(i)` returns `Result<String, InputError>`, failing `argument-missing` on an index outside the arguments. Results cannot be printed, compared, or used as ordinary values; handle them with `try` or `catch`.

The [example guide](syntax-examples.md) defines line endings, integer parsing, EOF, invalid UTF-8, prompts, and supported input domains. Prompts are written and flushed before reading. Redirected input is supported. Runtime input/output errors include source locations and exit nonzero; previous output remains visible. The interpreter checks the whole program, including unused word bodies, before any input or output occurs.

## Commands and validation

Run `go run ./cmd/zhex run examples/fibonacci.zhex`, or build with `go build -o bin/zhex ./cmd/zhex` and run `./bin/zhex run examples/fibonacci.zhex`. The runner requires a source file; `zhex repl [--trace]` instead starts an interactive session whose words and values persist across entries — a blank line ends a multi-line entry, bare expressions echo their value, errors print a diagnostic without ending the session, and `words` lists signatures.

Run `go test ./...` for the executable language cases and CLI tests. Run `go vet ./...` for Go checks. The [test catalog](tests.md) maps syntax and behavior to those tests. Additional named-type forms such as choices and aliases, maps, temporal values, broader resource scopes, and native compilation remain later work.
